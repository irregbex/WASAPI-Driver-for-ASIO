1. LAYERS
---------
ASIO host --IASIO (in-proc COM, ThreadingModel=Apartment)--> WasapiBridge --WASAPI-->
  Shared:    audiodg (mixing, SRC, APOs) -> miniport -> hardware
  Exclusive: miniport (WaveRT, DMA buffer) -> hardware
Capture sources: device (IAudioCaptureClient), device loopback
(AUDCLNT_STREAMFLAGS_LOOPBACK) and process loopback (VAD\Process_Loopback).

3. THREADING MODEL (invariants)
-------------------------------
H = host thread (the one that called init(); the DAW's UI thread).
A = audio thread (one per start()).
N = Windows threads: MMDevice notifications, volume callbacks, asynchronous
    loopback activation.

Rule 1: only H calls asioMessage() on the host (kAsioResetRequest,
  kAsioOverload, kAsioLatenciesChanged) and only H changes configuration,
  devices, streams and buffers.
Rule 2: A takes no locks, allocates no memory, writes no log and never calls
  asioMessage. It publishes to H with atomics + PostMessage(msgWnd).
Rule 3: N only queues (evQueue under evLock) and calls PostMessage(msgWnd).
  Exception: the volume callback reads IAudioEndpointVolume under a shared
  SRWLOCK (volLock); closeStreams takes it exclusively before releasing.
  0.9.8: each N callback object uses its owner only under its own shared
  lock; H detaches it (exclusive) before releasing or destroying anything
  (section 58.5).
Rule 8 (0.7.0): live settings. LiveParams (gain, dither, routing table, panel
  direct monitoring) are written only by H and published with SeqPublished
  (seqlock over atomic words, section 28); A copies them at the start of every
  wake-up and never reads cfg. Monitor ramps, monFeed and monScratch contents
  belong to A. The monitor window and the panel are H only.
Rule 9 (0.7.0): the crash handler runs on whatever thread faults; it touches
  only static data prepared by H and kernel events (section 32).
Rule 10 (0.8.0): the limiter state (limMain, limSink[], deficit, maximum
  reduction) belongs to A; H resets it in start() before creating the
  thread. A publishes the reduction through limGr (CAS maximum), H drains it
  with exchange in readMeters. The tray window, channel names, Bluetooth
  state, host profile and the SampleRate=Auto decision are H only; the
  format notification (N) is only queued like every other device event.
Rule 4: any call that may destroy the driver (a reset asioMessage) is the
  last thing the function does; MsgWndProc wraps it with AddRef/Release.
Rule 5 (0.3.0): meters, load and counter reset.
  A writes peakIn/peakOut with a CAS maximum (relaxed), clip*Mask with
  fetch_or, loadNow/loadMax with store. H reads the peaks with exchange(0)
  and the masks with load. The internal load state (loadEma, loadMaxA,
  loadSkip, qpcToLoad, loadAlpha) belongs to A only (H initializes it in
  start() before creating the thread, like samplePos). A reset requested by
  the panel is resetReq.fetch_or (bits WB_RESET_CLIPS / WB_RESET_STATS); A
  consumes it with exchange at the start of every wake-up. If no audio
  thread is alive, H clears only the atomics directly (never A's internal
  state).
Rule 6 (0.4.0): dither and sinc. ditherActive (H, when opening the output),
  sincTab (H, once in openStreams; never freed before the destructor, so a
  stuck thread never reads freed memory) and InputSource.sinc/posBase/target
  (H, when opening) are read-only for A. ditherState[] is A's state; H seeds
  it in start() before creating the thread. Profiles, the application list
  and PID resolution: H only (panel / openLoopback).
Rule 7 (0.5.0): extra devices. outEx/inEx, nOutEx/nInEx, lbFirst, nOutPrim,
  routeSrc/routeDefault and the streams of sinks[]/srcEx[] are set by H
  (resolveDevices / openStreams); A only reads them. Each sink's state
  (fifo, pos, ratio, fillEma, integ, primed, written) belongs to A; H resets
  it in start() before creating the thread. Counters and ratioView: atomics.
  Software volume of an Exclusive sink: volGain atomic, epVol under volLock
  like the main output (VolumeCallback with an index). A sink failure on A
  only publishes postReset(RR_DEVICE), once per cycle.

Message window (msgWnd): HWND_MESSAGE, class "WasapiBridgeMsg" registered
once per DLL load. This is how asioMessage is marshalled to H: every
thread that needs the host to act posts a message, and the window procedure
runs on H (the thread that created the window in init()). Messages:
  WM_APP+1 RESET     pendingReset (CAS RR_NONE -> reason) -> requestReset()
  WM_APP+2 DEVEVENT  drains evQueue -> handleDeviceEvent() per event
  WM_APP+3 OVERLOAD  pendingOverload -> asioMessage(kAsioOverload)
  WM_APP+4 DELETE    the last Release happened on A -> teardown() on H
  WM_APP+5 LATCHG    deferred kAsioLatenciesChanged (0.7.0)
  WM_APP+6/+7        create / destroy the monitor window (0.7.0)
  WM_APP+8/+9        create / destroy the tray window (0.8.0, section 38);
                     +9 is sent synchronously and needs no AddRef (it may
                     arrive from the destructor)
The window counts in g_objects until WM_NCDESTROY (the DLL cannot unload
while it exists). If the destructor runs on another thread, WM_CLOSE is sent
(DestroyWindow is only valid on the creating thread). It is created once per
instance.

4. IASIO LIFE CYCLE
-------------------
init(sysHandle)   hostWnd = sysHandle. LoadConfig, LogInit, msgWnd,
                  IMMDeviceEnumerator, resolveDevices(), DeviceNotifier.
resolveDevices()  FindDevice by substring (or the eConsole default; marks a
                  fallback). Channels = nChannels of the mix format
                  (<= MaxChannels). nIn = nInDev + 2 with loopback
                  (total <= 32). Reads Id, name and PKEY_Device_ContainerId
                  of input and output.
createBuffers()   Refused when called from A or while a stuck thread is
                  alive. If devicesDirty: LoadConfig + resolveDevices.
                  Contiguous float block numChannels*2*bufSize. Detects
                  support for kAsioSupportsTimeInfo, kAsioResetRequest,
                  kAsioOverload, kAsioLatenciesChanged. openStreams().
start()           Collects a thread that ended because of an error. Clears
                  FIFOs, counters, resampling and time state, peaks, clips,
                  load and resetReq; loadSkip = 8. ResetEvent(outEvent)
                  (stale signal). timeBeginPeriod(1) once (timerRaised).
                  cbRun = cb.
stop()            From A: only SetEvent(stopEvent). From H: SetEvent + wait
                  10 s. Timeout = thread stuck in a host callback:
                  threadStuck, stuckThread keeps the handle; streams and
                  buffers are leaked (not freed) and createBuffers/start
                  return ASE_HWMalfunction until that thread ends.
disposeBuffers()  Refused from A. stop + closeStreams + freeBuffers.
setSampleRate()   44.1..192 kHz. Reopens the streams; kAsioLatenciesChanged.
getLatencies()    out = bufSize + WASAPI buffer + GetStreamLatency.
                  in  = bufSize + input FIFO target.
getSamplePosition Seqlock: A increments tsSeq (odd = write in progress),
                  stores position and time, increments again (even =
                  stable). The reader retries while tsSeq is odd or changed
                  during the read: up to 1000 tries, SwitchToThread after
                  100; otherwise the last consistent pair.
controlPanel()    AddRef; ShowControlPanel; Release.
future()          kAsioCanTimeInfo, kAsioCanReportOverload: SUCCESS.
                  kAsioCanInputMonitor: SUCCESS if there is a device input.
                  kAsioSetInputMonitor: applied; loopback channels are
                  ignored with SUCCESS (so the host does not disable the
                  selector).
Release()         Last reference: on A -> SetEvent(stop) + WM_APP+4;
                  on H -> teardown(): stop(); if a stuck thread is alive the
                  object is leaked; otherwise delete.

5. OUTPUT OPENING
-----------------
Exclusive: period = max(10^7*bufSize/rate, minimum period). Candidates:
channels {mix, 2, 1} x {float32, int32, int32/24, int24, int16}.
IsFormatSupported(EXCLUSIVE) == S_OK -> Initialize(EVENTCALLBACK, p, p).
BUFFER_SIZE_NOT_ALIGNED -> GetBufferSize -> aligned duration for buffer and
period. DEVICE_IN_USE / EXCLUSIVE_MODE_NOT_ALLOWED -> Shared.
Low-latency Shared (LowLatencyShared and rate == mix rate):
IAudioClient3::GetSharedModeEnginePeriod -> InitializeSharedAudioStream(
EVENTCALLBACK, minPeriod, mix).
Standard Shared: Initialize(EVENTCALLBACK|AUTOCONVERTPCM|SRC_DEFAULT_QUALITY,
float32 x mix channels, mix channel mask).
outFmt.clamp = Exclusive (float > 1.0 is clipped; the Shared engine already
clips).
IAudioClock (0.3.0): Exclusive only, GetService on H when opening the
output + GetFrequency (not used if it fails or is 0). closeStreams releases
it (leaked when the thread is stuck, like render and outClient).
Volume: softVolume = Exclusive && !ENDPOINT_HARDWARE_SUPPORT_VOLUME;
volGain = mute ? 0 : 10^(dB/20).

6. INPUT OPENING
----------------
Exclusive (polled, no EVENTCALLBACK): periodicity = want; duration =
max(4*want, 4*output period). If not aligned, only the duration is aligned.
Capture period = want.
Low-latency Shared: IAudioClient3, minimum period raised in steps of the
fundamental period until per*3 >= 2*outPeriod; accepted if buffer >=
2*outPeriod. Otherwise standard Shared (AUTOCONVERTPCM, 20 ms).
FIFO target = capture period + outPeriod.
Drift correction (Auto): on unless the ContainerIds of input and output are
equal and known. Treated as unknown: the zero GUID and
{00000000-0000-0000-FFFF-FFFFFFFFFFFF} (shared by all built-in devices,
which may have different clocks: onboard codec vs HDMI).
Privacy (0.5.1): E_ACCESSDENIED when activating or initializing a capture
stream (main input, extra inputs, loopback; also in the Exclusive attempt
through lastExclHr) -> noteCaptureHr: a log line with the Settings path and
captureDenied (shown in the status); the driver continues without that
input.

7. LOOPBACK
-----------
ExcludeDaw / App: process loopback through ActivateAudioInterfaceAsync
(resolved from Mmdevapi.dll at runtime) on the virtual device
"VAD\Process_Loopback", with AUDIOCLIENT_ACTIVATION_PARAMS
{PROCESS_LOOPBACK, pid, mode}: ExcludeDaw = own PID +
EXCLUDE_TARGET_PROCESS_TREE; App (0.4.0) = PID of LoopbackApp +
INCLUDE_TARGET_PROCESS_TREE. pid and mode travel in ActCtx (written by H
before creating the activation thread).
App: FindProcessByExe on every openLoopback: one Toolhelp snapshot, every
match of szExeFile (case-insensitive) as {pid, parent}; the own PID is
dropped (if LoopbackApp is the DAW's executable, it is rejected).
Preference: the single root (a match whose parent is not a match; e.g. the
main process of a browser, whose tree includes the audio processes); with
several roots or none, the match that has an active audio session on some
output (ListAudioSessionPids, the same IAudioSessionManager2 walk the panel
uses); otherwise the first root or the first match. The PID and the reason
are logged. No process: log line and a source without a client (readSource
delivers zeros; the 2 Loopback channels still exist, nIn does not change).
The PID is not followed live: if the application restarts, it is resolved
again on the next open (Apply / host reset).
FollowDeviceChanges is not involved.
Activation thread details:
the activation runs on a dedicated MTA thread. The context (ActCtx) lives on
the heap with a reference count of 2 (host + thread): neither side writes
the other's memory after releasing it, so a late completion can never write
into a freed stack frame. The thread takes a reference to the DLL
(GetModuleHandleExW) and ends with FreeLibraryAndExitThread, so the DLL
cannot be unloaded under it. ActHandler implements IAgileObject (the
completion callback may run on any thread), counts in g_objects and releases
its client. Waits: thread 3 s for the activation; host 8 s for the thread.
Formats float32 2ch, then int16 2ch; LOOPBACK|EVENTCALLBACK|AUTOCONVERTPCM
with a dummy event (the stream is polled). Drift: corrected unless
DriftCorrection=Off.
All: loopback of the output device; same clock -> no resampling unless On.

8. AUDIO THREAD (run)
---------------------
audioTid; CoInitializeEx(MTA); MMCSS "Pro Audio" + AVRT_PRIORITY_CRITICAL.
Own references (AddRef) to render, output client, input and loopback clients
and capture clients, and IAudioClock (Exclusive only); cbRun is a copy of the
host callbacks. QueryPerformanceFrequency: qpcToLoad = 100 /
(freq * bufSize/rate); loadAlpha = 1 - exp(-(bufSize/rate)/0.3).
headroom = buffer >= 1.5 periods (only then does padding 0 mean a glitch).
Pre-fill with silence (written = buffer if it succeeded); Start capture,
loopback and render.
Loop: WaitForMultipleObjects({stop, render}, 2000 ms)
  1. wakeNs = timeGetTime*1e6; firstOfWake; now = QPC; applyResetRequest().
     Exclusive (0.3.0), from the 4th wake-up on and with cntSwitches > 0:
       with IAudioClock: a glitch only if played = GetPosition * rate /
       frequency >= written (the device played everything delivered); then
       written = played + buffer (re-synchronization: the normal state on
       wake-up is written - played ~ 1 buffer). Without IAudioClock
       (fallback): a glitch if now - prevWake > max(2 periods - 1 ms,
       period + 1 ms) (QPC). At most one glitch per wake-up: ++cntOutGlitch
       and WM_APP+3 as in Shared. prevWake = now.
  2. pullSource per source (returns true if the device became invalid; one
     RR_CAPTURE is published per cycle).
  3. Shared: padding; if 0 with headroom -> cntOutGlitch, WM_APP+3 (once
     pending). frames = buffer - padding. Exclusive: frames = buffer.
  4. while outFifo < frames: bufferSwitch(); if stopEvent is signaled ->
     leave.
  5. GetBuffer: AUDCLNT_E_BUFFER_TOO_LARGE in Exclusive = early event,
     continue (not added to written). writeOut -> ReleaseBuffer; on success,
     written += frames.
A 2 s timeout counts in cntTimeouts, and the next wake-up counts as a
glitch in Exclusive mode (it was real).
Leaving the loop: Stop/Reset, Release of the own references. On an error
HRESULT: lastHr, running = false, RR_WASAPI.

9. bufferSwitch / readSource
----------------------------
Priming: FIFO >= buf + target + 4.
Without resampling: copies bufSize frames; if short -> zeros, underrun,
re-prime.
With resampling (4-point Hermite, Catmull-Rom):
  k = floor(pos), t = pos - k, y = H(x[k-1], x[k], x[k+1], x[k+2], t),
  pos += ratio; floor(pos)-1 frames are consumed; pos stays in [1, 2).
  Time-normalized PI controller (src/drift.h, PiUpdate), dt = bufSize/rate:
    sp = target + buf/2                 (fill set point)
    fillEma += (1 - exp(-dt/1.0667)) * (fill - fillEma)
    e = (fillEma - sp)/sp               (normalized fill error)
    integ += 9.375e-6 * e * dt          (|integ| <= 0.002)
    ratio = 1 + 0.0005*e + integ        clamped to [0.997, 1.003]
  The EMA (time constant 1.0667 s) filters the packet granularity of the
  capture side; the proportional gain 0.0005 reacts to the fill error and the
  integral term (gain 9.375e-6 per second) removes the steady-state error,
  so the ratio settles exactly at the clock ratio. Because every constant is
  expressed per second (dt), the loop behaves the same for any buffer size.
  The ratio limit +-3000 ppm bounds the correction.
  Simulation (10 min, 480-frame packets): buffer 256 with +200/-300/+500/0
  ppm -> exact average, 0 underruns; -500 ppm -> 1 initial underrun; buffers
  64 and 2048 with -300 ppm -> converge, 0 underruns.
Time: ts = t0 + pos*1e9/rate. Only on the first block of each wake-up:
  drift = wakeNs - ts; if |drift| > max(50 ms, 3 buffers) re-anchor;
  otherwise t0 += drift*(1 - exp(-period/10 s)). publishTime(pos, ts) before
  the callback; bufferSwitchTimeInfo(samplePosition, systemTime, sampleRate,
  flags) or bufferSwitch.
Meters (0.3.0): after readSource, for every input with an active buffer,
  m = max|x| of the block; if m > 0: AtomicMax(peakIn[c], m) and, if
  m >= 1.0, clipInMask |= 1<<c. After the callback, the same with outBufs
  (what the host sends, before gain and volume) into peakOut/clipOutMask.
Load (0.3.0): QPC before and after the host callback;
  load = ticks * qpcToLoad (% of the block); loadEma += loadAlpha*(load -
  loadEma); the first loadSkip=8 blocks do not count for the maximum;
  loadNow/loadMax are published with relaxed stores.

10. writeOut
------------
gain = Gain * (softVolume ? volGain : 1). Direct monitoring added per frame
(monFifo; limited to 2*target + frames). Conversion: float (clipped in
Exclusive), int16 lrintf(x*32767), packed int24 lrintf(x*8388607), int32
llrint(x*2147483647). Extra device channels = 0; mono = (L+R)/2.
TPDF dither (0.4.0): ditherActive = Dither && Exclusive && integer && valid
bits <= 24 (ParseFmt reads wValidBitsPerSample). Per device channel,
xorshift32 (ditherState[c]); tri = ((s & 0xFFFF) - (s >> 16)) / 65536, a
triangular density in (-1, 1) LSB of the valid bits. Scaled by the valid
bits: q = 2^(valid-1) - 1, v = lrint(x*q + tri) clipped to [-q-1, q] and
written shifted left by (container - valid) bits: 16, 20 and 24 in packed
24, 20 and 24 in 32. Arithmetic in double (in float the tri would be lost
near full scale). Exact 0 is written without dither (digital silence).
Without dither (or float / 32 valid bits) the path is the 0.3.x one.

11. DIRECT MONITORING
---------------------
gain/0x20000000 (0 dB), pan 0..0x7fffffff with a constant-power law.
input -1 = all. monOut[i] = destination left channel or -1. monFifo is
cleared when monitoring is re-enabled (monWas) so that stale audio is never
played.

12. DEVICE NOTIFICATIONS
------------------------
DeviceNotifier -> queueDeviceEvent (queue bounded to 64) -> WM_APP+2 ->
handleDeviceEvent on H (if FollowDeviceChanges):
- The eConsole default changed and that side follows the default -> reset.
- The Id in use is no longer ACTIVE -> reset.
- The configured device becomes ACTIVE while a fallback is in use -> reset.
- An extra device disappears, or a missing extra device appears -> reset.
requestReset(): if the host has buffers and supports kAsioResetRequest, it is
sent once per start cycle; otherwise devicesDirty (re-resolved on the next
createBuffers).

13. PANEL: WINDOW OWNERSHIP AND LOOP
------------------------------------
(The 0.6.0 look is described in section 24; the ownership, loop, WM_QUIT,
timer and apply rules of this section still hold.)
Owner (0.5.1): PickOwner = GetActiveWindow() of the thread that calls
controlPanel (e.g. Cubase's Studio Setup dialog); if null, the foreground
window only if it belongs to the calling thread (0.6.0; before it was any
window of this process); otherwise hostWnd. The top-level ancestor
(GetAncestor GA_ROOT) is passed as hWndParent to CreateWindowEx (an owned
window: Windows keeps it in front of the owner and hands it the activation
while the owner is disabled). That owner (not always hostWnd) is disabled
while the panel is open and re-enabled before DestroyWindow so that focus is
not lost. Before 0.5.1 the owner was always hostWnd: after switching
applications and coming back, Studio Setup came to the front and the panel
stayed behind with no way to bring it back.
WS_EX_APPWINDOW: taskbar button and Alt+Tab entry, IDI_APPLICATION icon
(WM_SETICON). WM_ACTIVATEAPP (activation): SetWindowPos HWND_TOP without
activating. The name and routing dialogs are owned by the panel and disable
it the same way. "Copy status": the status text to CF_UNICODETEXT
(GlobalAlloc GMEM_MOVEABLE; if SetClipboardData fails it is freed and the
user is warned).
Own message loop: Ctrl+Tab / Ctrl+Shift+Tab are handled first
(HandleTabKeys), then IsDialogMessage. WM_QUIT from the host: the panel is
destroyed and WM_QUIT is re-posted. WM_DESTROY clears GWLP_USERDATA. Timer
500 ms -> getStatus(). Changes are applied only if the host still holds a
reference (hostHoldsRef). A non-standard buffer from the .ini is kept as an
extra combo item.
Meters (0.3.0): 50 ms timer (only while the panel is open) -> readMeters()
(exchange(0) of each peak, clip masks, active channels). Per-channel UI
state (MeterUi, H only): disp in dB falling at 24 dB/s, hold for 1.5 s
(GetTickCount). Click -> resetCounters(WB_RESET_CLIPS). "Reset counters" ->
resetCounters(WB_RESET_ALL). DPI of the host window (GetDpiForWindow loaded
dynamically; otherwise the system DPI). Centered in rcWork of the host's
monitor (MonitorFromWindow, MONITOR_DEFAULTTONEAREST).
Buttons: BN_CLICKED and BN_DOUBLECLICKED are handled alike (0.6.0), so a
fast second click on a toggle or push button is not lost.

%APPDATA%\WASAPI Driver for ASIO\log.txt / log-previous.txt. Only H and N

15. COUNTERS AND RESET (0.3.0)
------------------------------
WB_RESET_STATS clears: loadMaxA/loadMax, cntOutGlitch, cntTimeouts, input
and loopback underruns/drops/glitches, sink counters. WB_RESET_CLIPS:
clipInMask and clipOutMask. With a live thread (thread and
WaitForSingleObject(thread,0) == WAIT_TIMEOUT): only resetReq.fetch_or; if
the thread ends before consuming it, start() clears everything anyway. Peaks
are not reset (they are drained on every panel read).

16. LIMITS OF THE EXCLUSIVE GLITCH DETECTION
--------------------------------------------
- It depends on IAudioClock reporting the real device position. A stalled or
  late position does not produce false positives (played < written), but it
  can hide glitches (with a clock the late wake-up criterion is not used).
- Late wake-up (only without IAudioClock): threshold max(2 periods - 1 ms,
  period + 1 ms); with double buffering a delay below one period is
  inaudible.
- The first 3 wake-ups (the first event arrives right after Start) and those
  before the host's first callback are skipped.

Builds the report in memory (std::wstring), prints it (WriteConsoleW; UTF-8
when the output is redirected) and saves it as UTF-8 with BOM as
WasapiDriver-diagnostics.txt: exe folder, else %APPDATA%\WASAPI Driver for

Sections: RtlGetVersion (ntdll, GetProcAddress) + ProductName /

machine on ARM64); registration in KEY_WOW64_64KEY and KEY_WOW64_32KEY (ASIO
key, CLSID\{...}\InprocServer32, DLL existence, other ASIO drivers);
leftovers of the old name (ASIO keys, uninstall entry, program folder,
settings folder); ACTIVE render and capture endpoints (name, Id,
ContainerId, GetMixFormat, GetDevicePeriod,
IAudioClient3::GetSharedModeEnginePeriod, IsFormatSupported EXCLUSIVE at
44100/48000/96000 x float32/int32/int24/int24-in-32/int16 x 2ch,
IAudioEndpointVolume::QueryHardwareSupport and range); defaults per role;
MMCSS (service, AvSetMmThreadCharacteristics "Pro Audio" + critical priority
and revert, SystemProfile keys); config.ini (UTF-16LE with BOM) and the last
200 lines of log.txt (UTF-8), opened with FILE_SHARE_WRITE (the driver may be
writing).

18. AUTOMATIC TEST (WasapiDriverTest.exe, 0.3.1)
------------------------------------------------
Static x64 console program. STA main thread; CoCreateInstance(CLSID, IID =
CLSID, CLSCTX_INPROC_SERVER) like a DAW; init() with its own hidden window as
sysHandle. Every wait uses MsgWaitForMultipleObjects +
PeekMessage/DispatchMessage (never Sleep): the driver's message window lives
on this thread and kAsioResetRequest and kAsioOverload arrive through it.
Callbacks (the driver's audio thread): no locks, no allocation. A
preallocated record of 131072 entries {QPC, index, samplePosition,
systemTime} with an atomic counter; the main thread analyzes it after stop()
(stop waits for the audio thread). Outputs are zeroed in every callback.
asioMessage: answers kAsioSelectorSupported (ResetRequest, Overload,
LatenciesChanged, SupportsTimeInfo, EngineVersion), EngineVersion = 2,
SupportsTimeInfo = 1; every message is recorded with QPC in a fixed array.
Criteria: callbacks = span * rate / buffer + 1 (+-5% + 1; +-10% + 1 with
buffers >= 512, because of bursts aligned to the WASAPI period), alternating
indices, samplePosition + buffer exactly, non-decreasing systemTime,
getSamplePosition ASE_OK and monotonic (every 100 ms). T2: intervals >
max(100 ms, 4 blocks) = warning (count and worst value); more than 3 in the
10 s = FAILED. No callbacks within 3 s = FAILED and the test goes on.
States: PASSED, FAILED, SKIPPED (not applicable: a rate rejected by
canSampleRate or a buffer outside the range, as sub-results; T8 without a
physical input). SKIPPED does not count as a failure. Final line
"RESULT: PASSED" (", N warnings") or "RESULT: FAILURES = N".
T8 (--latency), audio thread state: 1 s of noise floor on input 1;
threshold = max(10 x noise, 0.01); an impulse of 0.5 at sample 0 of output 1
every second; round trip = position of the first |x| > threshold - impulse
position (0.5 s window); 10 detections or 15 impulses. The median is
compared with getLatencies (input + output). PASSED if the min-max spread
<= max(2, buffer/8) frames.

19. SINC RESAMPLER (0.4.0)
--------------------------
ResamplerQuality=Sinc replaces Hermite only for sources with active drift
correction (InputSource.resample) and for extra output sinks. The PI
controller (section 9) does not change.
Kernel (src/sinc.h): kSincHalf = 16 taps per side (32 in total), 256 phases
+ 1, Kaiser window with beta 8, cutoff at Nyquist (the ratio is ~1, there is
no decimation), each phase normalized to unity DC gain. A 257 x 32 float
table (32 KB) built once on H (BuildSincTable) in openStreams; it is never
freed before the destructor (rule 6).
Per output sample: k = floor(pos), t = pos - k; coefficients = linear
interpolation between phase floor(t*256) and the next one (SincCoefs, on the
stack); y = sum m=0..31 coef[m] * x[k - 15 + m]. The 32 FIFO pointers are
computed once per sample and reused for every channel.
Bounds: posBase = 15 (Hermite: 1); after consuming, pos is in [15, 16) and
consumed = floor(p) - posBase. need = pos + buf*ratio + 17 (Hermite: +3),
which guarantees highest index read < fill; lowest index k - 15 >= 0.
Priming and the pullSource drop reset pos = posBase.
Latency: target += 16 (filter look-ahead) when opening; this raises the PI
set point, the priming threshold and the reported input latency
(bufSize + target).
Offline test (tests/resampler_test.cpp, g++ on Linux; same float/double
arithmetic as readSource). Sine of 0.5, 48 kHz, fixed ratio 1.0002; RMS
error against the ideal signal, in dB relative to the signal (THD+N of the
resampling):
  Frequency    Hermite    Sinc 32x256 Kaiser 8
    1000 Hz     -91.6      -87.7
    5000 Hz     -47.5      -90.0
   10000 Hz     -26.6      -85.1
   15000 Hz     -14.7      -90.2
   18000 Hz      -9.7      -80.2
   20000 Hz      -7.1      -78.6
At 1 kHz Hermite is slightly better (the sinc floor is set by the linear
interpolation between 256 phases and float precision). The same test checks
the read bounds with ratios 0.997 / 1.0 / 1.003 and irregular arrivals: OK.
Cost: 64 MACs per frame to interpolate the coefficients + 32 MACs per
channel.

21. EXTRA DEVICES (0.5.0, beta)
-------------------------------
Configuration: ExtraOutputs / ExtraInputs (substring, up to 3, separated by
|). resolveExtras (H): FindDeviceSub (no default), the main device and
duplicates are ignored; channels = mix (MixChannels); if it does not fit in
32 (inputs: 32 - loopback) it is truncated or skipped with a log line;
missing = 2 silent channels (the count does not depend on it being
connected, unless it has a different count when it appears).
FindDeviceSub skips the Id of the main device and of extra devices already
chosen and goes on with the next match (two devices with similar names).
ASIO channel layout:
  outputs [0, nOutPrim) main; then outEx[k].asioFirst.. in order.
  inputs  [0, nInDev) main; then inEx[k]; lbFirst = end; Loopback L/R.
  Names: "N:Out L" / "N:In 3" (N = 1 main, 2.. extras) only if there are
  extra devices in that direction; otherwise the usual names.
Master clock: the event of the main output wakes A as always.
Extra inputs: srcEx[k] (InputSource) opened with openInput (the same code as
the main input, without Exclusive), Auto drift by ContainerId against the
main output, polled with pullSource on every wake-up and read in
bufferSwitch with readSource (no device: zeros).
Extra outputs (aggregate sinks): sinks[k] (OutputSink). Opening (H):
Exclusive only with Mode=Exclusive (initExclusive without an event: 4x
buffer); otherwise Shared AUTOCONVERTPCM|SRC_DEFAULT_QUALITY without an
event, buffer max(2*master period + 4*device period, 40 ms). Optional
IAudioClock. targetPad = master period + 2*device period (drift.h). sp
(FIFO) = ASIO buffer + master period (+16 with sinc). overLimit = 2*sp +
4*buffer + targetPad.
Feeding (A, bufferSwitch): after the host callback, the sink's ASIO channels
are copied into its FIFO (preallocated MultiFifo).
Servicing (A, on every wake-up, after reading the capture sources):
  1. pad = GetCurrentPadding; if FIFO > overLimit: drop to sp, overflow++.
  2. w = SinkFramesToWrite(pad, buffer, targetPad); 0 -> nothing.
  3. Priming: FIFO >= sp + need (the excess is dropped) -> primed;
     otherwise w frames of silence.
  4. need = pos + w*ratio + (3 Hermite / 17 sinc); if short: silence,
     underflow++, re-prime.
  5. ResampleFifo (same code as readSource) -> PutSample in the device
     format (device channels beyond the ASIO channels = 0), gain and
     software volume when applicable; consumption floor(p) - posBase.
  6. PI (PiUpdate, the constants of section 9) on the total fill =
     (FIFO - pos) + (queued - targetPad), dt = w/rate. queued = written -
     played, with played = GetPosition interpolated to the QPC time of the
     wake-up (IAudioClock); without a clock, queued = targetPad (FIFO only).
  A GetCurrentPadding/GetBuffer failure stops that sink and requests a reset
  (RR_DEVICE) once per cycle; the main output continues.
  Start: pre-fill targetPad with silence and Start before the master.
Latency: see section 23 (alignment). Direct monitoring is mixed after the
alignment delay line, with the main output's routing; kAsioSetInputMonitor
limits the destination to the main output's channels (destination >=
nOutPrim -> channel 0).
Dither: an integer Exclusive sink with <= 24 valid bits uses PutSampleDither
with its own state (OutputSink.ditherState, owned by A, seeded in start());
ditherActive is set by H in openSink.

23. DEVICE ALIGNMENT (0.5.0)
----------------------------
AlignDevices=1 (default) and at least one extra device open.
computeAlignment (H, in openStreams, before the FIFOs are sized) estimates
the latency of each path in frames:
  main output   = WASAPI buffer + GetStreamLatency
  sink          = sp (includes the sinc look-ahead) + targetPad + one master
                  period + the sink's GetStreamLatency
  input (main and extras) = target (includes sinc) + GetStreamLatency
  (Loopback does not take part.)
maxOut / maxIn = maxima. Aligning:
  - Main output: fixed delay primDelayFrames = maxOut - own, as a delay line
    on the physical channels (MultiFifo primDelay preallocated on H with
    capacity delay + buffer + 16; start() fills it with silence; writeOut
    pushes the routed frame and pops the oldest, with no allocation). It
    sits after the routing and before dither/clipping. Direct monitoring is
    accumulated separately (mt[], main output channels), goes through the
    same routing and is added AFTER the delay line: its latency is minimal
    with or without AlignDevices.
  - Faster sink: sp += maxOut - own (more FIFO; overLimit and capacity are
    computed afterwards).
  - Faster input: target += maxIn - own (raises priming, the PI set point
    and the drop thresholds).
getLatencies when aligned: output = bufSize + maxOut; input = bufSize +
srcIn.target (already shifted; without a main input: bufSize + maxIn).
Without alignment (or without extra devices): the usual values of the main
device.
Limit: these are estimates; drivers that do not report their stream latency
(Bluetooth, some USB) stay misaligned by that difference. The panel shows
each device's own latency and the common one.

27. CONFIG.INI COMMENTS AND PRINTED-OUTPUT PRIVACY (0.6.1)
----------------------------------------------------------
RewriteConfigFile (config.cpp, H only) runs at the end of LoadConfig,
SaveConfig, SaveProfile and DeleteProfile, after the profile API cache is
flushed. It reads config.ini (UTF-16LE with BOM; UTF-8 with BOM or the ANSI
code page are also accepted), drops every comment (';' or '#') and blank
line, keeps every section header and key=value line verbatim and in order
(unknown keys and every [Profile:x] section included), puts the English
comment block on top and a blank line between sections. If the result equals
the current text nothing is written (idempotent). Otherwise it is written
with a BOM to config.ini.tmp<pid> in the same folder, flushed, and moved over
config.ini with MoveFileExW(MOVEFILE_REPLACE_EXISTING |
MOVEFILE_WRITE_THROUGH); on failure the temporary file is deleted and the
old file stays. A crash leaves either the old or the new file.
src/privacy.h: SanitizeText replaces the values of %TEMP%/%TMP%,
%LOCALAPPDATA%, %APPDATA% and %USERPROFILE% (longest first,
case-insensitive) with the variable names, any other "X:\Users\<name>"
prefix with %USERPROFILE% (except Public and Default), and the user name and
computer name (whole words, 3+ characters) with <user> / <computer>.
ShortHash = "#" + 8 hex digits of the 32-bit FNV-1a hash of the lower-cased
text. Applied to: every log line (Log, H and N threads; never A), the whole
Diagnostics report and its console output (endpoint Ids and ContainerIds
hashed unless --full-ids), every line of the Test report and console, the
saved-report path messages, and the panel's "Copy status" text. Device Ids
in "Device change" log lines are hashed.

   H (panel Apply)                         A (audio thread)
   ---------------                         ----------------
   cfg = saved (LIVE keys)                 every wake-up:
   buildRoute() -> routeSrc[]                pubLive.tryRead(lv, lvSeq)

     LiveParams p = {gain, dither,             else copy words, re-check seq

SeqPublished<T> (src/live.h) stores T in std::atomic<uint64_t> words: the
writer never waits, the reader never waits (a torn read is detected by the

kAsioResetRequest. Hosts typically stop, dispose and recreate the buffers
(or reload the driver) asynchronously. The panel stays open and holds its
own reference (controlPanel AddRef), so even a host that releases the
driver meanwhile cannot free the object under the panel.

31. DIRECT MONITORING MIXER (0.7.0, F5)
---------------------------------------
Signal path on A (writeOut, one device frame at a time):

  capture packets --(same clock: pullSource)--------------+
  resampled input block --(drift corrected: readSource)---+--> monFifo
                                                                 |
  outFifo (host output) * gain -> routing -> alignment delay     |
                                     |                           v
                                     +-----(+)<--- mixMonitor(monFifo frame)
                                            |        host: per input, dest o,
                                            |              ramps to monGainL/R
                                            |        panel: pair -> pair,
                                            |              ramps to lv.dmG[]
                                            v
                                  SoftClip -> volume/clip -> dither -> device

- Ramps: dmix::Ramp, one-pole 5 ms (RampCoef), snaps to the target at
  1e-5 or when float precision stalls, so it ends exactly at 0 or 1 (no
  denormals). Ramps advance every frame, even when the FIFO is empty, so an
  "off" fades out; monFeed stays on until every ramp is 0.
- Pan: constant power (PanGains) for mono sources and the host's pan;
  balance (BalanceGains, never boosting) for a stereo pair.
- Clip safety: while monitoring, every physical channel passes SoftClip
  (identity to 0.9, tanh knee to 1.0) before conversion and dither.
- Meters: for monitored main channels, the peak of program + monitor (pre
  gain, like the other meters) is merged into peakOut once per writeOut.
- Bounded queue: monFifo is trimmed to 2 * (target [+ bufSize when
  resampled]) + frames; underruns count in monUnder and give silence.
- Exclusions: loopback channels (never in monFifo), extra outputs, no
  device input (dmOn false, monAny ignored).
Real latency: same clock = capture buffer + monFifo queue + output WASAPI
buffer; drift corrected = input FIFO target + one ASIO block + output
buffer. Never "zero latency".
kAsioSetInputMonitor: input -1..nInDev-1 (others ignored with SUCCESS),
output clamped to the main output, gain/pan converted with
AsioGainToLinear/AsioPanTo01; state off -> target gains 0 (the destination
is kept so it can fade out). kAsioCanInputGain/OutputGain: not supported.
tests/dmix_test.cpp checks ramps (largest step, settle time, no
denormals), pan and balance laws, ASIO conversions and the soft clipper.

32. CRASH PROTECTION AND SAFE MODE (0.7.0, F8)
----------------------------------------------
   H, driver constructor --> CrashInstall (once per process, ref counted)
        prune dumps to 5, LoadLibraryEx(dbghelp, SYSTEM32), events,
        dump thread (holds a DLL reference), AddVectoredExceptionHandler(0)
   any thread faults inside the DLL (address in [base, base+SizeOfImage))
        and the code is fatal (AV, illegal/privileged instruction, stack
        overflow, int divide/overflow, bounds, in-page, misalignment,
        noncontinuable, heap corruption):
        handler: one-shot flag, fill MINIDUMP_EXCEPTION_INFORMATION,
                 SetEvent(req), wait done (15 s), EXCEPTION_CONTINUE_SEARCH
        dump thread: crash-<yyyymmdd-hhmmss>.dmp (MiniDumpNormal |
                 MiniDumpWithThreadInfo) + crash-marker.txt, SetEvent(done)
   H, last driver destructor --> CrashUninstall: remove handler, SetEvent
        (quit); the thread closes its events and ends with
        FreeLibraryAndExitThread.
Faults are never swallowed and there is no longjmp: continuing after an
access violation would corrupt the host. Breakpoints and C++ exceptions are
not handled.
Session files: session-<pid>.txt is written at init and deleted when the last
driver object of the process is destroyed cleanly. The crash marker is
written ("dump pending") before the minidump and rewritten after it; the
faulting thread waits at most 5 s on {done, dump thread}.
Safe mode (init): marker present AND a session file of a process that is no
longer running (unclean exit; a marker alone is cleared) -> safe = true,
applySafeSettings() (Shared, default output, InputDevice=none, no extras,
no routing, Loopback=Off, DirectMonitor off, buffer 512, Hermite). cfg is
never saved; the panel and the monitor window use uiCfg (the saved
configuration, config()); cfg is only what is open. Exit: "Use my
settings again" (leaveSafeMode: clear marker, devicesDirty, postReset),
Apply in the panel, or disposeBuffers after a session that started (clean
session) -> marker cleared, safe mode stays for the current session.
Hardening: createBuffers rejects a null array, more channels than exist,
out-of-range or duplicate channels, and callbacks without any buffer
switch function; only a callback the host provided is ever called; every
getter checks its pointers.

35. HEARING-SAFETY LIMITER (0.8.0, G2)
--------------------------------------
src/limiter.h, header-only, used by A only:
   knee = ceiling * 0.708 (-3 dB)
   curve(x) = x                                         x <= knee
            = knee + (c - knee) * tanh((x - knee)/(c - knee))   x > knee
   per frame: peak = max |x[ch]|  (linked)
              d = deficit * (1 - rel); d < 1e-6 -> 0   (release, snap)
              need = 1 - curve(peak)/peak  if peak > knee
              deficit = max(d, need)  (instant attack)
              y = clamp(x * (1 - deficit), +-ceiling)  (rounding guard)
   rel = 1 - exp(-1 / (rate * 0.150))  (150 ms)
The release runs on the deficit (1 - gain): the form gain += (1 - gain) * rel
stalls about 2e-4 below 1.0 in float because the increment falls below half
an ulp of 1.0f (found by tests/limiter_test.cpp). No lookahead, no added
latency; the output can never exceed the ceiling because the frame's gain is
computed from the frame itself.
Position: main output: writeOut, after routing, the alignment delay and the
direct-monitoring soft clipper, before PutSample (integer conversion, clip,
dither). Extra outputs: serviceSink buffers one frame from the resampler
callback (frame-major order, channels 0..n-1) in a stack array, limits it,
then writes it. Each output has its own Limiter (limMain, limSink[k]).
Live parameters (LiveParams): limOn, limCeil (linear); the gain cap is
applied by H in publishLive (gain = min(gain, cap) while limOn && capOn), so
A has no extra branch. Keys: Limiter, LimiterCeilingDb (-20..-0.1),
LimiterGainCap, LimiterGainCapDb (-20..24); engine keys (stored in profiles).
Gain reduction: A writes limGr with a CAS maximum after each block; H
exchanges it in readMeters and keeps a per-consumer maximum (limGrAcc), so
the panel and the monitor window each see every peak. The UI holds a value
for 1 s.

39. CHANNEL NAMES (0.8.0, G6)
-----------------------------
Built by buildChannelNames() at the end of resolveDevices (H) into

  device part  ShortName(friendly name): "Speakers (X)", "Headphones (X)",
               "Line (X)", "Microphone (X)"... -> X; otherwise the whole name

54. LOW-LATENCY ENGINE AT ANY RATE: FIXED-RATIO CONVERSION AND ON-DEMAND
    CALLBACKS (0.9.4)
-------------------------------------------------------------------------
Suggested by Microsoft's Windows music team. IAudioClient3 shared streams
only run at the engine's mix format, so with LowLatencyShared=1 openOutput
always opens the main output at the mix rate:
  IAudioClient3 InitializeSharedAudioStream(min period)  (engineKind 1)
  -> IAudioClient3 at the default period                 (engineKind 1)
  -> IAudioClient::Initialize Shared at the mix format    (engineKind 2)
  -> Shared at the ASIO rate + AUTOCONVERTPCM (0.9.3)     (engineKind 0)
fr::Choose decides first (with the real channel count: every ASIO output
channel is converted, so OutputMap can route extra-device channels): no
exact ratio (den <= 4096, taps <= 1024) -> last step; rate down -> always
sinc, or Windows converts (last step) when taps x channels x rate exceeds
kMacBudget (150 M MAC/s); rate up -> sinc, Hermite above the budget (0.9.6,
KI-5: before, rate up followed ResamplerQuality, so the default Hermite was
used for 44.1 -> 48 kHz; ResamplerQuality now only selects the drift
resampler). The log text comes from fr::Describe (section 56). An IAudioClient3 period is accepted only if its buffer holds one
period plus one ASIO block; otherwise the next multiples of the fundamental
(up to 16, below the default) and the default period are tried.
Exclusive (engineKind 3) and Loopback are unchanged.

Converter (src/fixedratio.h, header-only, portable). num/den = inRate /
outRate in lowest terms (44100 -> 48000 = 147/160). Output frame j is the
input at exactly j*num/den: integer position k_ and phase ph_ (0..den-1),
ph_ += num, k_ += ph_/den, ph_ %= den, so there is no accumulated error.
Sinc: den coefficient sets (one per phase, built at open), Kaiser beta 10,
cut-off 0.95 x the lower Nyquist, half = 64 taps at the lower rate (64 /
ratio input taps when decimating: 70 for 48->44.1, 128 for 96->48).
Hermite: 4 points. ahead() = half (sinc) or 2: input frames needed after the
evaluated position = the converter's delay in input frames (the filter is
symmetric, linear phase). The ring is a power of two indexed by absolute
counters, followed by a mirror of its first taps frames (written lazily on
the next push / produce), so a filter window is always contiguous: the sinc
loop has no masking and no row table (stereo: two accumulators; other
counts: an array of 32); pushSlot / missingFor(n) / producible() / produce(n, out) are
allocation-free and lock-free. reset() writes ahead()-1 zeros of history
(start()).

Audio thread with conversion (run(), outConvOn):

  device event (every engine period P, device frames)
      |
      v
  GetCurrentPadding -> frames = outFill - padding      (outFill = FillTarget:
      |                                                 max(2P, P + block))
      v
  while outConv.missingFor(frames) > 0:     ASIO callbacks on demand
      bufferSwitch()  -- reads inputs for samplePos, host fills block,
      |                  bufSize ASIO frames pushed into outConv,
      |                  samplePos += bufSize, index flips
      v
  outConv.produce(frames) -> outFifo (device rate) -> writeOut
      (gain, routing, delay line, monitor, limiter) -> render buffer

So callbacks happen exactly when the device needs data, at the average rate
of the ASIO clock (ASIO rate / bufSize per second), with a jitter of at most
one engine period plus one block (the model measures 10.9 ms max at P=480,
96 kHz device, 44.1 kHz ASIO). samplePosition advances by exactly bufSize
per callback; systemTime = sched::BlockClock: t0 + pos/rate, re-anchored on
the first block of each wake-up (tau 10 s, jump > 3 x fill or 50 ms).

Inputs (openInput, LowLatencyShared=1 and not Exclusive): opened at the
input's own mix rate (IAudioClient3 with a period >= 2/3 of the output's,
else standard Shared at the mix format), s.conv = device rate -> ASIO rate.
pullSource decodes each packet into s.conv and drains producible() frames
into s.fifo (qMade counts them). Same clock as the output (no drift
correction): alignedIn, frame q of the FIFO is delivered at samplePosition
q + inDelay, with
  inDelay = B + aheadOut + ceil((aheadIn + 1 + capPeriod) x Ra / Rin)
            + ceil(P x Ra / Rd)
(sched::InDelay), which makes the round trip constant and equal to the
reported latencies. readSource checks the frames ready beyond the block
(model: 2-3 periods in steady state); outside [0, exHi] (output dropout,
late capture start) it re-aligns to exMid and counts an underrun / drop.
Inputs on another clock keep the drift PI after the converter (target +=
converter delay). Inputs whose mix rate equals the ASIO rate do as before.

Latencies (getLatencies = sched::ReportLatencies, the same function the
model checks, ASIO frames, plus the user offsets):
  output = B + aheadOut + round((outFill + streamLatency) x Ra / Rd)
           (sched::OutLatency; primOutLat = output - B, used by alignment)
  input  = B + target; aligned converted input: target = inDelay - B -
           aheadOut (sched::InLatency) reported as is (the block is already
           in it), so in + out = round trip = device part + inDelay
outPeriodAsio = P x Ra / Rd replaces outPeriod wherever an ASIO-rate amount
is meant (input targets, sink set points, alignment).

Direct monitoring (monPath, set at open): 1 = capture packets (input at the
output device's rate and clock), 2 = delivered blocks (output not
converted), 0 = not available (converted output, input at another rate or
on another clock; logged). With monPath 0 kAsioCanInputMonitor returns
ASE_NotPresent; a change of availability between two opens of the same
instance sets monResetPending and posts WM_WB_RESET (requestReset from the
message window). The panel's direct-monitoring note shows S_DM_NORATE.

Extra outputs keep the standard Shared stream at the ASIO rate with
AUTOCONVERTPCM: they are serviced on the master's wake-ups and need a buffer
of several master periods, which an IAudioClient3 stream (buffer = one
period) does not give (CODE-REVIEW AI3).

Engine line: openOutput builds engineLine (English, log "Engine: ...",
private ASIOFuture selector WB_FUTURE_ENGINE_INFO for WasapiDriverTest T2);
the panel builds a translated line from StatusInfo (engineKind, outDevRate,
mixRate, outConv, convSinc).

Offline model: src/sched.h Sim reproduces run() (device wake-ups, FillTarget,
both converters, the aligned input FIFO) and tests/fixedratio_test.cpp runs
6 rate pairs x periods 128/144/256/480 x buffers 32..1024 for 10 simulated
minutes each (accounting, xruns, callback timing, re-alignment window) and
5 s with an impulse through output converter, device buffer, stream
latency, a loop-back cable and the input converter: measured round trip =
reported within 0.5 frames.

58. HARDENING (0.9.8): EXCEPTION BARRIER, HOST VALIDATION, BOUNDED WAITS, TRACING
--------------------------------------------------------------------------------
Goal: whatever a host (or a dependency: Windows audio drivers, config.ini,
the GitHub API) passes to the driver, the driver must answer with an error
and keep the host process alive; it must never let a C++ exception, an
out-of-bounds access or an unbounded wait reach the host. The audio engine
and every valid call behave exactly as in 0.9.7. Findings and fixes:
CODE-REVIEW.txt "0.9.8 hardening review" (H1-H32).

58.1 Exception barrier (src/guard.h)
  Every function the outside world calls is a C / COM / Win32 boundary. The
  standard library reports allocation failure only by throwing, so
  -fno-exceptions is impossible; instead each boundary catches everything:
    IASIO methods         AsioCall (driver.cpp): the body is a lambda; any
                          exception -> ASE_HWMalfunction (std::bad_alloc ->
                          ASE_NoMemory), logged and traced. init() ->
                          ASIOFalse with an error message.
    IUnknown              QueryInterface null out pointer -> E_POINTER;
                          Release() catches around teardown().
    Class factory, DLL    CreateInstance (the constructor can throw through
    exports               CrashInstall's allocations: now noexcept),
                          DllGetClassObject, DllRegisterServer /
                          DllUnregisterServer; LockServer never goes below 0.
    Window procedures     registered as GuardedWndProc<P> (DefWindowProcW on
                          an exception); the hidden message window catches
                          inside (its WM_NCDESTROY bookkeeping always runs);
                          the button subclass, the message-box CBT hook
                          (CallNextHookEx) and the EnumWindows callbacks
                          (GuardedEnumProc: stop enumerating) too.
    COM callbacks         DeviceNotifier::forward (a failed allocation drops
                          the event), VolumeCallback (nothing allocates),
                          ActHandler (null operation checked).
    Threads               audio thread (threadProc, outside the loop),
                          update worker (kErrUnavailable), loopback
                          activation (nothrow allocations), dump thread and
                          hold thread (stack and Win32 only).
    Destructor            ~WasapiBridge runs its work in a try block; the
                          bookkeeping (critical section, crash protection
                          reference, object count) runs in every case.
    Control panel         the message loop of ShowControlPanel is wrapped,
                          because its PanelState lives on that stack frame.
    Log()                 noexcept (scope guard on the critical section; a
                          failed allocation drops the line, never writes it
                          unsanitized).
  NoteException logs the first 16 contained exceptions and emits the
  ExceptionContained event. The audio thread allocates nothing on the
  real-time path, so the guard sits only at its thread procedure: no cost
  while no exception is in flight (table-based unwinding).

58.2 Host arguments and call order (src/asiocheck.h)
  A pure header (no Windows, no ASIO SDK) holds every rule; driver.cpp maps
  its results 1:1 to ASIOError (static_assert on the values) and
  tests/asiocheck_test.cpp drives it with 200000 random calls.
    State machine     Created -init-> Initialized -createBuffers-> Prepared
                      -start-> Running. Before init: ASE_NotPresent. start
                      before createBuffers: ASE_InvalidMode.
                      getSamplePosition while stopped: ASE_SPNotAdvancing.
                      outputReady: ASE_NotPresent. disposeBuffers (any
                      state) and setClockSource(0) (also before init) answer
                      ASE_OK as in 0.9.7 (independent review R2: hosts that
                      dispose defensively must never see an error).
    Rates             NaN, infinities, negative and non-standard rates:
                      ASE_NoClock; setSampleRate(0) = no change.
    createBuffers     callbacks present with bufferSwitch or
                      bufferSwitchTimeInfo; size 32..4096 (any value: the
                      preferred size of config.ini may be any value, so
                      granularity -1 is advertised but other in-range sizes
                      are accepted, as before); numChannels 1..nIn+nOut;
                      every channel in range for its direction (isInput: any
                      non-zero value is an input); no channel twice. All
                      checks run BEFORE existing buffers are disposed.
    Copy once         the host's ASIOCallbacks are copied into cbStore (the
                      audio thread never follows the host's pointer again);
                      the channel list is copied by CopyInfos, which reads
                      each host field exactly once, and only the copy indexes
                      the buffer tables; getChannelInfo and
                      kAsioSetInputMonitor read their structures once. A host
                      changing its memory concurrently cannot pass a check
                      with one value and use another (TOCTOU).
    Thread            setSampleRate, controlPanel and createBuffers are
                      refused on the audio thread (they would wait for the
                      thread itself or run a modal loop on it).
    Private selector  WB_FUTURE_ENGINE_INFO (test tool) needs an EngineInfo
                      header (magic + size); a host passing that selector
                      value with any other buffer gets ASE_InvalidParameter
                      instead of a 256-byte write.
    Strings           getDriverName / getErrorMessage copy fixed sizes that
                      fit asio.h's 32 / 124 bytes (static_assert).

58.3 Untrusted device data
  Mix formats are used only if writeOut / pullSource can handle them inside
  the frame (DevFmtUsable: 1..1024 channels, block = channels x bytes, int
  2/3/4 bytes, float 4 bytes); otherwise Windows converts (AUTOCONVERTPCM,
  a format the driver builds itself). Periods and latencies
  (REFERENCE_TIME) become frames through RefTimeFrames (clamped to 0..2^24;
  the double -> UINT32 conversion of a huge or negative value was undefined
  behavior). A device buffer of 0 or more than 2^20 frames is refused (main
  output) or closes that source (inputs, extra outputs), and MultiFifo::init
  clamps frames (2^22) and channels (1024), so no FIFO size computation can
  overflow size_t on the 32-bit build. pullSource reads at most 256 capture
  packets per wake-up.

58.4 Waits
  Wait                                  Bound    On timeout
  ------------------------------------  -------  -----------------------------
  stop(): audio thread end               10 s     thread marked stuck; its
                                                  objects and buffers are kept
                                                  (stuckAlive)
  start(): audio thread still exiting    10 s     same (was INFINITE before)
  run(): render event                    2 s x 5  ends the thread with
                                                  HRESULT_FROM_WIN32(ERROR_TIMEOUT),
                                                  reset requested (a device that
                                                  stops signaling without a
                                                  notification); WAIT_FAILED ends
                                                  it at once (it used to be taken
                                                  for a render event). Review
                                                  R5: before ending, the device
                                                  position (IAudioClock, or the
                                                  Shared padding) sampled at each
                                                  timeout is checked; if it moved,
                                                  the count restarts (e.g. resume
                                                  from Modern Standby)
  process-loopback activation            3 s / 8 s  E_ABORT
  crash handler on the faulting thread   5 s      returns (no dump)
  dump thread: request / quit events     INFINITE  by design: no device IO, quit
                                                  always signaled by the last
                                                  CrashUninstall
  update worker (WinHTTP)                10/10/15/30 s per operation, 2 / 10 min
                                                  per job; cancellable
  HoldThread WaitForInputIdle            10 s
  Not boundable: the IAudioClient calls themselves (Initialize, Start, Stop,
  Reset) have no timeout parameter; a hung Windows audio driver blocks the
  calling thread inside Windows. On the audio thread this is covered by the
  10 s stop() bound; on the host thread nothing can be done. SendMessageW to
  the hidden window from another thread (monitor / tray destruction) waits
  for the host's UI thread; a timeout there would let a window outlive the
  driver (use after free), so it is kept.

58.5 Notifications without use after free
  DeviceNotifier and VolumeCallback hold an SRW lock shared while they use
  their owner; detach() takes it exclusively and clears the owner. Once
  detach() returns no callback is inside the driver, so the driver can be
  destroyed even while Windows delivers a notification. Before, a callback
  could load the owner pointer, lose the CPU, and use it after the driver had
  been freed. Release() also sets `dying` on every thread now, so the hidden
  window ignores the object while it is being destroyed.

58.6 Lock order (no ABBA)
  DeviceNotifier::lock -> evLock;  VolumeCallback::lock -> volLock;
  any -> g_logCs (Log never takes another lock);  g_installLock (crash) ->
  none of the driver's locks;  instance registry lock -> none (tryAddRef is
  atomic). H never holds evLock, volLock or g_logCs while it takes a
  callback lock (detach runs with no lock held), and no lock is held while
  calling the host (asioMessage) or WASAPI register/unregister functions.
  The audio thread takes no lock at all.

59. ARM64X DLL: BUILD, CHECKS AND REGISTRATION (0.9.9)
------------------------------------------------------
What it is. WasapiDriverARM64X.dll is one PE image (machine AA64, flagged
ARM64X) with two code halves compiled from the same sources: native ARM64
code and ARM64EC code (ARM64 instructions that follow the x64 calling
convention and data layout, so they interoperate with x64 code in the same
process). A native ARM64 process sees the image as an ARM64 DLL; an x64
process running under emulation (Prism) sees, through the ARM64X dynamic
relocations, an ARM64EC image with its own export table, so its calls land
in the ARM64EC half and run natively, without emulating the driver. This is
the target Microsoft recommends for in-process audio components (ASIO
drivers, plug-ins) on Windows on Arm, because one file and one
registration serve both kinds of host.

Build (scripts/build-arm64x.ps1, "arm64x" job of build.yml at every push
and of release.yml; GitHub windows-11-arm runner, MSVC from the image via
ilammy/msvc-dev-cmd with arch arm64):
  rc         src\WasapiDriver.rc -> obj\res.res (one resource section)
  cl         each DLL source twice: native (obj\a64) and /arm64EC
             (obj\ec); /O2 /EHsc /std:c++17 /W3 /MT /utf-8 /permissive-
             /Zc:__cplusplus, the same defines as the mingw builds plus
             _CRT_SECURE_NO_WARNINGS and NOMINMAX
  link       /dll /machine:arm64x, /defArm64Native:<def> (exports of the
             native half) and /def:<def> (exports of the EC half), both
             object sets, the same import libraries as the mingw builds;
             <def> is obj\WasapiDriverARM64X.def, a copy of
             src\WasapiBridge.def with "LIBRARY WasapiDriverARM64X" (the
             real output name; avoids LNK4070), EXPORTS unchanged
  static CRT (/MT): no Visual C++ runtime DLL is needed on the user's PC.
The sources needed two portability fixes, both C++ conformance issues that
GCC and clang accepted (CODE-REVIEW.txt "0.9.9 MSVC / Arm64X"): no
preprocessor directives inside macro arguments (dll.cpp), and no identifier
"small" (a macro in rpcndr.h; panel.cpp). In dll.cpp _M_ARM64EC is tested
before _M_ARM64 / _WIN64 because the EC compiler also defines _M_X64 and
_WIN64; the DriverLoaded trace event reports "ARM64" or "ARM64EC", which is
how a test shows which half a host loaded (TEST-GUIDE.txt block Z).

Checks (the script fails when one fails; GitHub then packages nothing):
  dumpbin /headers     machine line contains ARM64X
  dumpbin /exports     exactly DllCanUnloadNow, DllGetClassObject,
                       DllRegisterServer, DllUnregisterServer
  dumpbin /dependents  no vcruntime*, msvcp*, msvcr*, concrt*, ucrtbase*
                       (other non-system DLLs are reported as warnings)
Messages are classified (compiler and LNK1xxx / LNK2xxx errors -> ::error,
compiler and LNK4xxx warnings -> ::warning, 10 of each) and the script
always ends with one ::notice annotation (result, machine line, exports,
imported DLLs, SHA-256): annotations are visible on the public run page,
the job summary is not. The job outputs ok=true and sha256 only on success.
Expected warning: LNK4279 (SetFilePointerEx mapped to different icall push
thunks, static UCRT objects vs update.obj), benign: see CODE-REVIEW.txt.

Packaging. "build" (both workflows) needs "arm64x" and runs under
!cancelled(), so a failed or skipped arm64x job never blocks it. It
downloads the DLL only when arm64x reported ok, verifies its SHA-256
against the job output, and then (release.yml) signs it with the other DLLs
and stages it next to them: makensis gets -DARM64X=1 and the bin zip takes
it with *.dll. Otherwise a ::warning "No Arm64X DLL" is written, the
package is built exactly as in 0.9.8, and the release notes say that the
package has no Arm64X DLL. package-trusted re-signs every DLL of the bin
zip and rebuilds the Setup with -DARM64X=1 when the DLL is in it.

Registration. Windows on Arm has two registry views, as x64 Windows: the
native 64-bit view and WOW6432Node for 32-bit processes (x86 and ARM32).
Emulated x64 processes are NOT redirected: they read and write the same
64-bit view as native ARM64 processes. So a single InprocServer32 value in the 64-bit view is what both an ARM64
host and an emulated x64 host use to load the driver. Before 0.9.9 that
value could name only one of WasapiDriverARM64.dll (an emulated x64 host
cannot load a pure ARM64 DLL) or WasapiDriver64.dll (a native ARM64 host
cannot load an x64 DLL), hence the Setup's question. With the Arm64X DLL the
same value serves both: the loader maps the native half into an ARM64
process and the EC half into an x64 process.
  Setup (installer/WasapiDriver.nsi): ARM64X is defined by -DARM64X=1 or,
    at compile time, by the presence of ..\WasapiDriverARM64X.dll
    (-DARM64X=0 forces it off). On a machine where ${IsNativeARM64} is true
    the DLL is installed and RegCom writes, in the 64-bit view, the same
    keys as for every other DLL (CLSID default name, InprocServer32 = the
    Arm64X path, ThreadingModel = Apartment, the ASIO key); no question.
    The installer writes the keys itself, as it always did; the DLL's
    DllRegisterServer (which would write the same keys for its own path in
    the view of the calling process) is not used. RegCom overwrites the
    InprocServer32 value, so an upgrade from 0.9.8 or earlier, which had
    registered the ARM64 or the x64 DLL there, leaves exactly one 64-bit
    registration. The 32-bit view keeps WasapiDriver32.dll. The plain ARM64
    and x64 DLLs are still installed (unregistered), as a manual fallback.
    On x64 Windows the Arm64X DLL is not installed. Without ARM64X the
    0.9.8 code path (question, ARM64 or x64 DLL) is compiled unchanged, and
    a stale WasapiDriverARM64X.dll in the program folder is deleted. The
    uninstaller deletes the file and, as before, the keys of both views;
    WaitFilesFree includes the Arm64X DLL.
  install.bat: on ARM64, if WasapiDriverARM64X.dll is in its folder it is
    registered (reg.exe /reg:64) without the 1 / 2 question; the 32-bit
    registration is unchanged. uninstall.bat needs no change (same keys).
  Diagnostics: the 64-bit view report shows the Arm64X path; nothing else
    changes (the tools stay x64; on Windows on Arm they run emulated, so
    WasapiDriverTest.exe loads the ARM64EC half: it is the x64-host test).
Status: built and checked in CI; not yet run on real Windows on Arm
hardware (KNOWN-ISSUES.txt KI-9).

60. SOXR ENGINE OF THE FIXED-RATIO CONVERTER (0.9.10)
----------------------------------------------------
What. A third engine for the fixed-ratio converter of section 54 (used when
the ASIO rate differs from the device rate with LowLatencyShared=1, e.g. a
44.1 kHz project on a 48 kHz device, in both directions): the SoX Resampler
library (soxr 0.1.3, LGPL-2.1-or-later, third_party/soxr, vendored files
unchanged; THIRD-PARTY-NOTICES.txt section 6). Steinberg built-in ASIO
Driver 1.0.9.26 installs soxr.dll next to asiobtin.dll, and asiobtin.dll
loads it for sample-rate conversion (its binary contains the message "Cannot
load soxr.dll! No SRC!"); observed by inspecting the installed files.
Requested by the maintainer, who
decided that the default stays low-latency: soxr is used ONLY when the user
selects it ("soxr (best quality, +8-10 ms)"); the default Auto is exactly
the 0.9.9 behaviour.

Setting. config.ini FixedRatioEngine=Auto|Soxr|Sinc|Hermite (cfgtypes.h
FrEngine, parse.h, config.cpp; an engine key: written to every profile,
RESET key in NeedsReset; default Auto). Panel: Advanced tab, "Quality" card,
"Rate conversion" combo (ID_FRENG; items "Auto (Sinc, low latency)" /
"soxr (best quality, +8-10 ms)" / "Sinc (low latency)" / "Hermite
(light)"; help tip S_TIP_FRENG with the measured trade-off (Auto/Sinc 1.5 ms,
115 dB SNR; soxr 132 dB SNR, no aliasing, ~8-10 ms more at 44.1-192 kHz,
more at 16-32 kHz) and the RESET tag;
strings in en/es/pt/fr/de). The two top cards of the Advanced
tab are 36 px taller, the cards below moved down by 36 (the last one now ends
at y 594 of 624).

Policy (fixedratio.h, pure, tested): Choose(in, out, ch, budget, pref):
  no exact ratio (SincTaps == 0)                     -> None (Windows), any pref
  pref Hermite and the rate goes up                  -> Hermite
  pref Soxr and SoxrMacs <= budget                   -> Soxr
  SincMacs <= budget                                 -> Sinc
  over budget: rate down -> None, rate up -> Hermite (the 0.9.6 rule)
  Auto never picks soxr: Auto and Sinc both give the 0.9.9 rule (Auto exists
  so a later version can refine the automatic choice without changing an
  explicit Sinc), and with Auto the log line is the 0.9.9 one word for word
  ("sinc (12 M MAC/s, budget 150 M)"). An explicit Soxr over the budget falls
  back to that rule and the log says why. Hermite is
  never used to lower the rate (no anti-aliasing): pref Hermite then follows
  the sinc rule. SoxrMacs = kSoxrMacsPerFrame (64) x channels x (in + out
  rate), soxr's CPU time expressed in sinc multiply-accumulates (measured 13
  to 38 per channel and input + output frame on the development x64
  machine and 52.1 for 48 -> 44.1 kHz on another x64 machine in the
  independent review; 64 leaves about 20 % margin; 0.9.10 development used
  48). Cost(Soxr) = SoxrMacs, so the shared budget of review R2 (one
  150 M budget per stream open: output first, then the inputs) applies
  unchanged. With this model soxr is cheaper than sinc for every standard
  pair, so an explicit Soxr gives soxr or, over the budget, Hermite (up) /
  Windows (down). Describe() log texts: "soxr HQ (12 M MAC/s equivalent,
  budget 150 M)", "Hermite (FixedRatioEngine=Hermite)", and for Soxr over
  the budget the fallback's text followed by "; soxr HQ not used: it would
  cost 215 M MAC/s equivalent, over the budget of 150 M"; the 0.9.6 texts
  are otherwise unchanged.
  The engine line (Status tab, Copy status, test tool) says "internal rate
  conversion 44100->48000 Hz (soxr HQ, look-ahead 429 frames)"; inputs log
  "<tag>: internal rate conversion ... (soxr HQ, look-ahead 420 frames)".
  If soxr refuses a pair or fails (not seen), configure() falls back to
  sinc; the driver then decides again with fr::FallbackFromSoxr (the sinc
  rule with the same remaining budget: sinc, or Hermite going up / Windows
  going down if sinc does not fit, since soxr is cheaper than sinc in the
  cost model), subtracts the cost of what it really uses, and logs "soxr not
  available (<soxr message>); instead: <Describe text>" (independent review,
  item 6). The trace events OutputOpen and InputOpen carry ConvEngine =
  "soxr HQ" / "sinc" / "Hermite" ("" without conversion; TRACING.txt).

Recipe. soxr_quality_spec(SOXR_HQ, 0): 20-bit precision, linear phase, pass
band to 91.3 % of the lower Nyquist frequency (<= 0.01 dB specified, 0.004 dB
measured), stop band from 100 %. Engine "cr32" (single precision, plain C;
soxr-config.h enables nothing else: no SSE / AVX / NEON engine, no OpenMP).
soxr_runtime_spec(1) with log2_min_dft_size = log2_large_dft_size = 10: the
DFT length of soxr's FFT stage is then the smallest soxr allows for that
stage's filter: the filter length times 1.7 to 3.4, rounded to a power of two,
at least 1024 points (1024 for the 409-tap filter of 44.1 -> 48 kHz; longer
filters, e.g. for strong decimation, get 2048 or more; with soxr's default
log2_large_dft_size = 17 it would be about 4 times the filter length).
EnsureFftTables covers lengths up to 2^17.
Measured choices (44.1 -> 48 kHz with a standalone probe: look-ahead in
input frames before the 16-frame margin, CPU of soxr_process in ms per
second of stereo audio on the x64 test machine, two runs averaged):
  HQ, FFT up to 2^17 (soxr default)   925 (21.0 ms)   3.3 ms/s
  HQ, smallest DFT (chosen)           413 (9.4 ms)    3.8 ms/s
  VHQ (28-bit) on cr32                378 (8.6 ms)    4.9 ms/s, but the float
                                      engine cannot deliver 28 bits, and the
                                      double engine (cr64) would cost more
  MQ (16-bit, wider roll-off)         430 (9.8 ms)    3.5 ms/s, less quality
HQ with the smallest DFT length halves the look-ahead of soxr's default
for about 15 % more CPU, still less than half of what sinc costs.

Latency (the converter's contract, frsoxr.h). soxr pre-loads its filters, so
its output is time-aligned with the input (an impulse at input frame k comes
out at exactly k * den / num; the test checks it within 0.25 frame) and the
converter adds no shift. What it adds is buffering: an output frame becomes
available only when the FFT block containing it was computed. SoxrCore
measures, at configure(), for a mono instance fed one frame at a time over
2 s of input, the largest number of input frames needed beyond an output's
position, and adds 16 frames of margin: that is ahead(), used exactly like
the sinc look-ahead by missingFor / producible (so the driver pushes ASIO
blocks until soxr has the frames) and by sched::OutLatency / InDelay (so the
latency reported to the host includes it). soxr_delay() is not used: it
returns the output owed for the input consumed so far, which varies with
the block phase; ahead() is its worst case in input frames.
  pair             look-ahead soxr      sinc            Hermite
  44.1 -> 48 kHz   429 (9.73 ms)        64 (1.45 ms)    2
  48 -> 44.1 kHz   420 (8.75 ms)        70 (1.46 ms)    2
  48 -> 96 kHz     430 (8.96 ms)        64 (1.33 ms)    2
  96 -> 48 kHz     845 (8.80 ms)        128 (1.33 ms)   2
  44.1 -> 96 kHz   429 (9.73 ms)        64 (1.45 ms)    2
  96 -> 44.1 kHz   824 (8.58 ms)        140 (1.46 ms)   2
At lower rates the look-ahead is longer (the FFT blocks hold the same number
of samples): 32 <-> 48 kHz 8.0 ms, 44.1 -> 22.05 kHz 19.2 ms, 48 -> 16 kHz
15.6 ms, 16 -> 44.1 kHz 26.8 ms (sinc 2-4 ms there). So soxr adds about
8-10 ms per converted direction at 44.1-192 kHz, more at 16-32 kHz: at
44.1 kHz ASIO on a 48 kHz device with a 128 buffer and a 144-frame engine
period the reported output latency is 888 frames (20.1 ms) instead of 523
(11.9 ms); a converted input adds the same again to the round trip. This is
why soxr is opt-in and the default Auto stays on sinc (KNOWN-ISSUES.txt
KI-10). The scheduling model (sched::Sim with soxr in both converters, 48
cases: 6 rate pairs, periods 144 / 480, buffers 32 / 128 / 512 / 1024, 10
simulated minutes each plus 5 s with real samples) measures the impulse
round trip equal to getLatencies in + out within 0.50 frame, with exact
accounting, no underrun and no promised frame missing.

Real-time safety (where soxr allocates; frsoxr.h header has the details).
  soxr_create        allocates everything (filters, FFT setup, FIFOs): host
                     thread, configure().
  soxr_process       never allocates, except that a stage FIFO (fifo.h)
                     grows with realloc() when a write does not fit.
  soxr_clear         frees and re-creates everything: never used.
  global FFT table   (fft4g_cache.h) grows with realloc() when an instance
                     needs a longer FFT than any before; without OpenMP its
                     lock is a no-op, so another stream's audio thread could
                     read freed memory: EnsureFftTables() grows it to 2^17
                     points once per process before the first soxr_create.
Measures: Feed() passes at most 128 frames per soxr_process call and drains
all output after each call (FIFO contents stay at about one FFT block plus
one call's output); configure() warms the instance up with 2 s of silence
in pseudo-random pieces of 1..128 frames (host thread); reset() (start(),
host thread) does not call soxr_clear but pushes 2 x ahead + 64 frames of
silence (rounded up to a multiple of num, so the output grid stays exact)
and discards the output up to there; the FIFO allocator of soxr is ours
(soxr-config.h: FIFO_MIN = 64 so a FIFO compacts instead of growing,
fifo-headroom.c: every FIFO starts with 64 KB and grows to twice what it
asks for). soxr_create also calls getenv (SOXR_* runtime overrides) and
time(): host thread only, and ahead() is measured with the same settings.
Verified: tests/fixedratio_test.cpp counts soxr's malloc / calloc / realloc
on the audio-thread path (-Wl,--wrap): 0 over 52 million output frames of
random driver-like traffic (5 pairs, output and input patterns, reset()
between runs); a separate stress run over every exact pair of 22.05, 32,
44.1, 48, 88.2, 96, 176.4 and 192 kHz (220 configurations, 1..4 channels,
random buffers and requests, 30 s each, 3 seeds): 0 allocations, 0 missing
frames (CODE-REVIEW.txt 0.9.10; before the FIFO policy and the small calls,
that run found a few realloc calls at 32 -> 192 kHz and 48 -> 32 kHz).
Costs: configure() runs the look-ahead probe (mono, 2 s of input: about
5-15 ms at 44.1-48 kHz, more at 192 kHz) and the warm-up (2 s of silence for
every channel). Measured: 11-17 ms for a stereo pair opened the first time,
3-9 ms afterwards; with the probe result cached, 40-51 ms for 8 channels and
about 150 ms for 32 channels (development machine; the independent review
measured 196-270 ms for a first 32-channel open on a fast x64). The probe
result depends only on the rate pair, so SoxrCore keeps it in a lock-free
per-process cache (32 slots, key = rate pair, host threads only): later
opens of the same pair skip the probe; the test checks that the cached
look-ahead equals a fresh probe. The warm-up is kept for every open: it is
what guarantees that soxr's FIFOs never grow on the audio thread;
memory about 200 KB per converted channel (64 KB per soxr FIFO). A promised
frame that soxr had not produced (never seen) would be played as silence and
counted; closeStreams logs the count if it is not 0.

61. INPUT FIFO OVERFILL LIMITS AND THE CAPTURE BUFFER (0.9.11, KI-13)
---------------------------------------------------------------------
Every capture source feeds a MultiFifo (ASIO-rate frames) from pullSource
(audio thread, after every wake-up and, since 0.9.11, after every host
callback of a wake-up, section 62). pullSource drains every packet the
IAudioCaptureClient reports and then bounds the fill: without drift
correction the fill is the input latency, so a real surplus must be
dropped, with drift correction the PI controller keeps the fill at its
set point and a surplus means the controller lost track; the aligned
converted path (section 54) only guards the capacity because readSource
discards what is older than the next block itself.

Up to 0.9.10 the limits were, in ASIO frames,
    plain:    bufSize*2 + target*3      (drop to bufSize + target)
    drift:    bufSize*4 + target*6      (drop to bufSize + target, pos reset)
    aligned:  inDelay + bufSize*4 + exHi*2   (drop to half of it)
and ignored how much the capture client can hand over in ONE call. A
polled Exclusive capture (initExclusive with event=false asks for a buffer
of 4 x the output period or 4 x the ASIO buffer, whichever is larger; the
device may round up, 1536 frames for a 256-frame period on a tested USB
interface) delivers everything its buffer holds when it is read: if the
audio thread read it one period late, or the device driver fills it in
bursts, one call brings most of the buffer. That is real audio (every
frame is played by the device exactly once), but with 768 frames already
waiting (bufSize + target after a normal read) a 1536-frame call reached
2304 > 2048 and 1536 frames were dropped. The symptom (first recording
test, 0.9.10): about 10 drops per second, no underruns, no
discontinuities, an unusable recording at a 256 buffer; clean at 512,
whose limit (4096) the bursts did not reach.

0.9.11 adds the capture buffer, in ASIO frames (ceil(bufFrames * rate /
devRate) for a converted source, bufFrames otherwise), to the three limits.
A backlog of the whole capture buffer can never trigger a drop; a surplus
larger than that is still dropped as before. openStreams sizes every FIFO
as base + capture buffer x4 + target x6 (+ inDelay), so each limit lies
below the capacity (MultiFifo::pushSlot would otherwise overwrite the
oldest frame silently).

Diagnostics (atomics kept by the audio thread, read by getStatus on H and
by the Stats trace event every 10 s; the audio thread never logs or
traces): per source capPulls, capEmpty (no packet), capMulti (2 packets or
more), capMaxPkt (largest packet, device frames), capMaxWake (most frames
in one call), capMaxFill (highest fill after a call). "Copy status" prints
them for the main input ("Capture: pulls ... max FIFO fill ... frames");
the Stats event carries CapturePulls .. CaptureMaxFifoFill. They are reset
with the other counters (start, Reset counters). Reading them in a report:
max packet = the capture period; max per wake close to the capture buffer
= the thread is sometimes a period late or the device bursts (harmless
since 0.9.11); max FIFO fill growing from report to report = a real
surplus (clock mismatch without drift correction).
capEmpty close to half of capPulls is normal with two callbacks per
wake-up (section 62): the extra pull between the callbacks usually finds
no new packet. The capture buffer in ASIO frames is computed once per
open (InputSource::capBufAsio, openStreams), not on the audio thread.

What the 0.9.11 counters showed (block AB, 2026-10-25, the same interface
with the manufacturer's driver, 44.1 kHz): in Exclusive mode at a 256
buffer the polled capture client reported a 512-frame packet (up to 1024)
at EVERY 256-frame output wake-up ("pulls" at the wake-up rate, "empty 17
of 8368"), i.e. twice real time; the FIFO grew 256 frames per wake-up and
the limit above discarded real audio every 16-17 wake-ups (504 drops in
50 s). At 512 the packets were 512 per 512-frame wake-up and balanced. The
limit therefore only moved the drop point; the remedy is not to poll an
Exclusive capture at all (section 64). The limits and counters stay as
described for the polled (Shared, loopback) sources.

0.9.12 additions to the diagnostics: fillNow (fill after the last drain;
"max FIFO fill N (now M)": a large steady "now" means the plain copy path
keeps a backlog it once received, i.e. the real input latency exceeds the
reported one until the stream restarts), pullGapMaxUs per source and
wakeGapMaxUs for the thread ("max gap: wake X ms, read Y ms", section 64),
and a one-time clearing of every statistics counter one second after the
start (outWakes >= ceil(outDevRate / outPeriod), through resetReq /
applyResetRequest, section 64): the start-up transient (priming, the
host's first callbacks, the capture engine settling) counted 1 underrun /
2 discontinuities in the first 85 wake-ups of an otherwise clean run.

62. CAPTURE DRAINED BETWEEN HOST CALLBACKS; LATE-PACKET MARGIN (0.9.11, KI-11)
------------------------------------------------------------------------------
The audio thread wakes on the output event (section 54: engine period, 480
frames = 10 ms in the low-latency Shared engine), drains the capture
clients, and then runs as many host callbacks as the output needs: with
an ASIO buffer shorter than the engine period (256 at 44.1 kHz against a
441-frame period) two callbacks per wake-up, more with on-demand
conversion. Up to 0.9.10 the capture clients were drained only before the
callbacks. A Shared capture stream opened with IAudioClient3 has a buffer
of about two periods (974 frames here); while the host processed two
callbacks (its DSP load peaks were up to 45 %) the engine could fill it,
and when the capture buffer is full the Windows engine discards packets
and flags the next one with AUDCLNT_BUFFERFLAGS_DATA_DISCONTINUITY (the
driver counts it as a discontinuity / "glitch"; the missing frames then
show as an underrun). Observed in the first recording test: 8 underruns
and 27 discontinuities in 30 s at 256, none at 512 (one callback per
wake-up).

0.9.11: pullAll (the lambda in the audio thread) is called at the start of
the wake-up as before AND after every bufferSwitch of the wake-up while
more callbacks are needed (both loops: the on-demand conversion loop and
the plain outFifo loop). Cost: one GetNextPacketSize per source and
callback when nothing arrived. The same reset bookkeeping applies (one
RR_CAPTURE reset per cycle).

Late-packet margin: the FIFO target of a Shared source is capture period
+ output period (ASIO frames); priming waits for bufSize + target + 4. The
Windows engine delivers capture packets with up to one period of jitter.
With one callback per wake-up a late packet is covered by the target; with
two callbacks per wake-up the second one could find less than bufSize
frames (1142 - 512 - 512 < 256 after a late packet) and underrun, which
also re-primes the source (silence until the fill recovers). 0.9.11 added
one capture period to the target when bufSize < capture period (ASIO
frames). Block AB on 0.9.11 then showed the same loss at 512 (22
underruns / 46 discontinuities in 85 s, "max per wake 970" = the whole
974-frame capture buffer): a 512 block consumed the FIFO down to about 390
frames before a late packet. 0.9.12: the margin is added at EVERY buffer
size, for Shared sources, the loopback source and the event-driven
Exclusive capture (section 64; its packets arrive on their own event, out
of phase with the output). The log says "FIFO target +441 frames
(late-packet margin of one capture period)" and the reported input
latency includes it (10 ms at 44.1 kHz with the Windows engine, at every
buffer size now). The aligned converted path (section 54) keeps its own
exact schedule (sched::InLatency) and is not affected by the margin.

63. EXCLUSIVE FALLBACK REASON (0.9.11, KI-12)
---------------------------------------------
initExclusive (section 9) tries every candidate format at the ASIO rate and
returns false when none is accepted; openOutput / openInput then open
Shared. Up to 0.9.10 only the log told, and the panel's Mode combo
(Exclusive) contradicted the status ("Active mode: Shared ..."). The usual
cause is a device whose own driver fixes the rate (the Windows "Default
format" is greyed out): IsFormatSupported(EXCLUSIVE) refuses every format
at any other rate.

0.9.11: initExclusive records, for the FIRST failure of an open only
(independent review R1: a later attempt, the main input after a failed
output or an extra output, keeps the first reason), exclFailRate (the rate
tried), exclFailHr (the last Initialize HRESULT, 0 when IsFormatSupported
refused everything) and exclFailMix (the endpoint's mix-format rate, read
with GetMixFormat on the activated client before the attempts) in the
driver (H only; cleared by openStreams); the callers set exclFail = 1
(output) or 2 (main input, when the output succeeded). getStatus copies
them with exclusiveWanted = cfg.exclusive. The panel: with exclFail = 1
the "Active mode" line becomes "<mode> (Exclusive not available at R Hz;
the device is fixed at M Hz by its own driver or the Windows default
format)" when the mix rate differs from the ASIO rate, "<mode> (Exclusive:
no format accepted at R Hz)" when exclFailHr is 0, else "<mode> (Exclusive
refused, hr=0x...)"; with exclFail = 2 the same note follows the device
name on the Input line. The bottom bar shows S_SUM_EXCLFALL (output) or
S_SUM_EXCLFALL_IN (input) in amber while the streams are open and
Mode=Exclusive is configured. The log line reads "Exclusive: no format accepted at R Hz (the
device's shared-mode rate is M Hz: its own driver or the Windows default
format fixes it)". Planned for 1.0: when the ASIO rate is refused, open
Exclusive at the mix rate and run the fixed-ratio converter (section 54)
on the Exclusive stream.

Control panel notes (0.9.11): "Apply and Close" (IDOK runs Apply and, when
it returns true (ApplyResult::Live or ResetRequested), the IDCANCEL path:
owner re-enabled, DestroyWindow; for ResetOnReload, "saved only" and a
saved host-profile mapping the panel stays open showing applyMsg). Enter
on the panel presses the default button, so Enter applies and closes too.
The button is 170 px wide so the
longest translation ("Übernehmen und schließen") needs neither the small
font nor an ellipsis (LayoutAudit); the bottom-bar summary rectangle ends
60 px earlier. The DSP line of the status names the engine that converts
the main output (outConv / convSinc / convSoxr) and, only while drift
correction runs, the drift resampler's kind (StatusInfo::sinc).

64. EVENT-DRIVEN EXCLUSIVE CAPTURE (0.9.12, KI-13)
--------------------------------------------------
Up to 0.9.11 an Exclusive capture (Mode=Exclusive, the main input) was a
POLLED stream: initExclusive(event=false) asked for a periodicity of the
ASIO buffer size and a buffer of four periods, and the audio thread
drained it from the output wake-up (pullSource: GetNextPacketSize /
GetBuffer / ReleaseBuffer until no packet is left). How a device driver
answers GetNextPacketSize in that mode is its own business: the Yamaha
Steinberg USB Driver (UR22mkII) reported 512-frame packets at every
256-frame wake-up (section 61), and no limit or margin on the driver's
side can repair audio that is reported twice.

0.9.12 opens the Exclusive capture EVENT-DRIVEN, the mode the output has
always used:
- openInput activates a probe IAudioClient, reads GetDevicePeriod and
  takes the DEFAULT period D (the minimum period if the default is below
  it), in frames at the ASIO rate. The periodicity asked for is the
  smallest multiple of D that is >= HALF the ASIO buffer (D itself when
  half a buffer fits in one period). 0.9.12 asked for a whole buffer
  (independent review R1 (3): an event-driven stream double-buffers one
  period, and the host callback for one block must never last longer
  than that window); 0.9.13 halves it because the two periods of the
  double buffer together cover one block, and because the capture gate
  (section 65) no longer depends on when the packets appear. 512 at
  44.1 kHz: 441 (reported input latency about 41 ms instead of 63 ms
  with the 882-frame period of 0.9.12); 1024: 882.
  initExclusive(..., event=true, periodFrames) asks for periodicity =
  buffer = that value (AUDCLNT_STREAMFLAGS_EVENTCALLBACK requires equal
  values; the AUDCLNT_E_BUFFER_SIZE_NOT_ALIGNED retry keeps period =
  aligned buffer). A multiple of the device's default period is what its
  driver processes natively, so every event carries exactly one real
  packet; a periodicity of the driver's own choice (the ASIO buffer) is
  what the polled mode asked for and what the tested driver answered
  wrongly. The log says "period P (device default)", "(K x device
  default)" or "(aligned by the device; default D)".
- InputSource::event (auto-reset, created by H in openInput, closed by H
  in closeSource; leaked, like the COM references, when the audio thread
  is stuck) is set with SetEventHandle; eventDriven = true. start()
  resets it (a stale signal from the previous run).
- The audio thread waits on {stopEvent, capture events, outEvent}
  (WaitForMultipleObjects with the real count; one handle per
  event-driven source, the main input and, should an extra input ever
  open Exclusive, srcEx[k]). Index 0 stops, indices 1..n drain THAT
  source (pullSource once; its packet is the period) and go back to
  waiting (no output work, no host callback), index n + 1 is the output
  wake-up (unchanged flow). The order matters (review R1 (1)):
  WaitForMultipleObjects returns the LOWEST signalled index, so a packet
  pending together with the output event is drained before the long
  output service. pullAll (the start of the output wake-up and the pulls
  between host callbacks, section 62) drains the polled sources (Shared
  inputs, loopback) and, in addition, any event-driven source whose event
  is already signalled (WaitForSingleObject(event, 0) consumes the
  auto-reset signal; review R1 (2)), so a packet that arrived during a
  host callback is taken before the next one can overwrite it.
- FIFO target of the event-driven source: capture period + output period
  + one capture period of margin (section 62), all in ASIO frames; the
  overfill limits of section 61 apply unchanged (capBufAsio = one period).
- Idle detection: before 0.9.12 a dead output stream showed as five
  WAIT_TIMEOUTs of 2 s. With capture events waking the thread every
  period that timeout would never fire, so the check is time-based: an
  "idle tick" (probePosition of the output, cntTimeouts, the five-ticks
  rule with the "still moving" exception of review R5) runs when the Wait
  times out AND when a capture event arrives 2 s or more after the last
  OUTPUT event, at most once per 2 s (lastOutEventQpc, lastIdleTickQpc).
  The outcome is the same as before: ten seconds without an output event
  and a frozen device position end the stream with ERROR_TIMEOUT.
- Fallback: when GetDevicePeriod fails, CreateEvent fails or
  SetEventHandle fails, the input opens Shared and the status / panel
  report it as an Exclusive fallback (section 63, exclFail = 2).
- Known limit: the device double-buffers one capture period. A packet is
  lost (the device flags a discontinuity) only when the thread does not
  drain it within one period, i.e. when one host callback (one ASIO
  block, the longest uninterruptible stretch of the output service)
  lasts longer than the capture period. (3) makes the period at least one
  ASIO block, (1) and (2) drain before and between callbacks, so that
  needs a host callback that takes longer than its own block time: that
  is an output dropout too (the DSP load is above 100 %).
- Start-up clearing (review R2): one second after the start (outWakes
  >= ceil(outDevRate / outPeriod)) the thread sets resetReq |=
  WB_RESET_STATS and applyResetRequest, called right after, clears every
  statistics counter (the same set as the panel's "Reset counters").
  cntTimeouts counts real Wait timeouts only (review R3).
- Log: "Input open (Exclusive, event-driven): 2ch int24, period 441
  (device default), buffer 441, FIFO target 1323, ...". Status: "Input:
  <name>  [2ch int24, event-driven, period 441]". Trace InputOpen:
  EventDriven = true.
Timing counters (section 61, 0.9.12): wakeGapMaxUs (longest interval
between two output wake-ups, written on the output path) and
pullGapMaxUs per source (longest interval between two drains, written in
pullSource) are QueryPerformanceCounter differences (qpcFreq is set by
the thread before its loop); both are capped at 4e9 us, cleared with the
counters and by the one-second start-up clearing. Reading them: a large
"wake" gap together with discontinuities = the audio thread was held (a
long host callback, the system); a small gap with discontinuities = the
capture engine glitched by itself.
Not changed: Shared capture (polled from the output wake-up and between
callbacks: the Windows engine answers GetNextPacketSize correctly), the
loopback source, the extra inputs (always Shared), the output path.

65. THE CAPTURE GATE: ONE PERIOD PER PERIOD, BY A TRUSTED CLOCK (0.9.13 / 0.9.14, KI-13)
-----------------------------------------------------------------------------------------
What block AB on 0.9.12 showed (Steinberg UR22mkII, Yamaha Steinberg USB
Driver, 44.1 kHz, Exclusive, event-driven capture): at a 256-frame ASIO
buffer with a 441-frame capture period the drain ran 172 times per second
(the rate of the OUTPUT wake-ups) and every drain found one 441-frame
packet (empty 3 of 7255): 172 x 441 = 76 000 frames per second, 1.73
times real time, the FIFO grew, the overfill limit discarded real audio
(427 drops, 13 discontinuities). At 512 with the 882-frame period of
0.9.12 the drains ran 50 times per second (one per period) with 882-frame
packets and everything was balanced. So, with this driver, neither the
capture event nor GetNextPacketSize marks real periods: whenever the
thread asks, the driver answers "one full period is ready", and the event
fires at a rhythm of its own (the output period here).

0.9.13 gated every drain of an Exclusive source by the capture stream's
own IAudioClock. Block AB on 0.9.13 showed that this clock is part of the
same broken accounting: at Exclusive 256 it advanced by one period at
every drain (gated 0, 384 drops, 6527 drains in ~38 s at 172 per second,
one packet each). A clock that moves with the packets cannot gate them.

0.9.14: the reference is a clock the driver already trusts.
(InputSource::gate / gateQpc; pullSource, audio thread)
- Reference, decided by H at open (gateQpc): when the output is Exclusive
  with a usable IAudioClock (outClock, the one the output's glitch
  detection uses, sections 5, 8 and 16) and the source is on the same hardware as
  the output (same container id, the sameBox test of the drift policy),
  the gate runs on the OUTPUT stream's clock: one device, one hardware
  clock, and the output's position is real time (it plays with 0
  glitches). The position is converted to device frames exactly like the
  glitch detection (frames = position x rate / frequency); in Exclusive
  mode the input runs at the output's rate (section 6). Otherwise (the
  input is on another device, the output is Shared, no clock) the gate
  runs on the system timer. The capture stream's own clock is not used.
  Shared and loopback sources have no gate (the Windows engine answers
  GetNextPacketSize correctly).
- A sets aOutClk / aOutClkToFrames for the run before starting the
  streams. When the main input is gated by the output clock the OUTPUT
  stream is started first (independent review of 0.9.14: the base must be
  a position of a running clock; a stopped clock would make the base
  stale by the start-up delay) and the capture Start is followed by
  gateArm, which records the output position (review M1 of 0.9.13: a
  non-blocking GetPosition; the first drain therefore already sees one
  period of new audio). The decision of open (gateOutRef) is kept and
  every start() derives gateQpc from it again, so a run that fell back to
  the timer does not pin the next one. Every drain computes
  avail = output frames played since that base - frames accepted so far.
  A position that went backwards (device reset, counter wrap)
  re-synchronizes the base (M2); a backlog above four periods is not
  replayed (M3: the accepted count jumps, the capture buffer could not
  hold more anyway). Below 7/8 of a capture period NOTHING is read (the
  drain returns at once, counted in capGated: the "gated" number of the
  Capture line; it still counts as a pull and as a read for the "read
  gap" counter, L1). Otherwise the first packet is always taken and the
  next one only while the frames of this drain plus its size stay within
  avail + period/8 (decided before reading, H1): avail in [0.875 p,
  1.875 p) gives exactly one packet, a real backlog (the thread was late,
  avail grew meanwhile) two or more. Over time exactly one period is
  accepted per period, whatever the driver offers and however often the
  thread asks.
- System timer reference (gateQpc, chosen at open or after a failed
  GetPosition of the output clock, one way, no flapping): a credit of
  elapsed time x device rate (QueryPerformanceCounter) bounded to four
  periods above zero (a long stall is not replayed) and two periods below
  (a packet taken a little early is paid back by the next elapsed time,
  H2), the same 7/8 and +1/8 rule on the credit. The system timer and the
  device clock differ by parts per million; the plain copy path absorbs
  that as a slow fill drift that the overfill / underrun logic bounds (an
  underrun or a drop every many minutes at most). capGateRef tells which
  reference is in use (0 none, 1 output clock, 2 timer: the Stats event
  and the stop line of the log, "clock=output|qpc").
- The event and pullAll (section 64) are unchanged: they decide WHEN the
  thread asks; the gate decides whether a packet is taken. An event that
  fires too often costs a refused drain (a non-blocking GetPosition and a
  comparison); one that fires too late is covered by the double buffer
  and the late-packet margin, as before.
- Everything on this path is a non-blocking COM query or arithmetic: no
  allocation, no lock, no log, no trace (project rule). The log reports
  the gate at open ("capture gate on the output stream's clock (same
  device)" or "... on the system timer (...)") and at stop ("input
  capture gate: pulls=N gated=M clock=output|qpc|none").
What to expect in block AB on 0.9.14 (Exclusive 256, 441-frame period):
"pulls" about 172 per second as before (taken and refused drains both
count), "gated" about 72 of them per second (the drains that found no new
period), "max packet" = "max per wake" = 441 (one packet per taken
drain; 882 only after a late wake-up), drops 0, discontinuities 0, "read
gap" about one output period, and "clock=output" in the stop line.
