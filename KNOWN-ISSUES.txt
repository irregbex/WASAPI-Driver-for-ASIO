WASAPI Driver for ASIO - Known issues and field observations
=============================================================

This file records problems seen during real-world testing (Windows 11
(Insider build), Cubase 15, DaVinci Resolve Studio 21, Bluetooth earbuds
(A2DP, 10 ms minimum period), a USB audio adapter, HDMI monitor audio and a
USB audio interface). Each entry lists the symptom, what the logs showed,
the cause (confirmed or suspected), the workaround and the status.

Status values: FIXED (version), CONFIRMED (cause known, not a driver bug),
UNDER INVESTIGATION, OPEN (driver bug, fix pending).


KI-1  Opening DaVinci Resolve cuts all Windows audio (YouTube, recordings)
---------------------------------------------------------------------------
Status: CONFIRMED - caused by another ASIO driver, not by this driver.
Note (0.9.11): current DaVinci Resolve versions have I/O Engine = "System Audio" (Preferences > System > Audio
I/O), which uses Windows audio directly and loads no ASIO driver; with it this issue cannot occur and this driver is
not needed for Resolve (FAQ 14).
Note (2026-10): this was the OLD "Generic Low Latency ASIO Driver" (asioglld.dll). Steinberg's
current "Steinberg built-in ASIO Driver" (asiobtin.dll, 1.0.9 of 18 December 2024) is a different driver; in our test it
ran in shared mode and other apps kept playing. Its panel still shows the old name in some
languages (see FAQ.txt question 19).

Symptom
  - Audio playing in other apps (e.g. YouTube in a browser) stops the moment
    DaVinci Resolve starts, and does NOT come back by itself.
  - The browser recovers only when playback is restarted (moving the
    YouTube position marker).
  - Snipping Tool screen recording with system audio stops with
    "Audio stopped during recording. Check the connection."
  - Apps started afterwards (e.g. MPC-HC) play normally.
  - Resolve itself may be silent at first.

What the logs showed
  - The WASAPI Driver for ASIO log for the Resolve session is normal:
    Shared mode, IAudioClient3, 48000 Hz, no conversion, no exclusive mode,
    no errors.

Cause
  - On the "LOADING FAIRLIGHT ENGINE" splash screen, Resolve first loads the
    "Generic Low Latency ASIO Driver" (installed by Steinberg software).
    That driver opens the audio device in EXCLUSIVE mode.
  - When a device is taken exclusively, Windows invalidates every shared
    stream that was playing on it. Apps that do not handle the
    "device invalidated" event (most browsers mid-playback, screen
    recorders) stop until they reopen their stream.
  - Resolve then switches to the ASIO driver selected in its preferences.
  - Resolve's preferences did not always show which driver was really in
    use; after removing the Generic driver Resolve fell back to the next
    ASIO driver it found (the ASIO driver of a USB audio interface that has
    its own ASIO driver).
  - Cubase does not show the problem because it loads only the selected
    ASIO driver.

Workaround
  1. Uninstall "Generic Low Latency ASIO Driver" (Settings > Apps) if it is
     not needed. Close every Cubase / Resolve process first (Task Manager),
     otherwise Windows reports it as in use; reboot if needed.
  2. In Resolve: Preferences > System > Audio I/O > select
     "WASAPI Driver for ASIO", save, restart Resolve.

Documentation to add
  - FAQ entry: "Some programs probe other ASIO drivers at startup. Exclusive
    drivers (Generic Low Latency ASIO Driver, ASIO4ALL in some modes) will
    interrupt Windows audio while they are loaded."


KI-2  Cubase process stays running after File > Quit
-----------------------------------------------------
Status: CONFIRMED - caused by an old third-party plugin in one project,
not by this driver.

Symptom
  - After closing Cubase, its process remained in Task Manager with 0 % CPU
    and its memory still allocated (three hung instances accumulated over
    several sessions).
  - Side effects:
    - The driver installer could not replace WasapiDriver64.dll ("in use").
    - A hung Cubase that had the Generic Low Latency ASIO Driver open kept
      the audio device in exclusive mode (see KI-1): no sound anywhere until
      the process was ended, and the Generic driver could not be uninstalled.
    - The PC felt slow while the hung processes were alive.

What the logs showed
  - The driver log always ended with "Driver released": the driver finished
    its own shutdown (streams closed, buffers disposed, object destroyed).

Tests
  - Generic Low Latency ASIO Driver uninstalled: Cubase still hung with the
    old project, so the Generic driver was not the cause.
  - New empty project, one new instrument, played, saved, File > Quit with
    WASAPI Driver for ASIO: Cubase closed normally.
  - Conclusion: an old plugin used by the recovered project does not release
    correctly when Cubase quits.

Workaround
  - Task Manager > Cubase > End task. Identify the plugin by disabling the
    project's plugins one by one (or loading the project in safe mode) and
    update or replace it.

Installer improvement (0.9.6, independent of the cause)
  - The installer (and the uninstaller) now detects locked DLLs: before
    changing anything it checks that WasapiDriver64.dll, WasapiDriver32.dll,
    WasapiDriverARM64.dll and the two tools can be replaced. If one is in
    use (a DAW, or a hung host process, has the driver loaded) it asks the
    user to close the audio programs (Cubase, DaVinci Resolve, Ableton
    Live, ...) or end the hung process in Task Manager, with Retry /
    Cancel, instead of failing or leaving the old DLL in place. Cancel
    leaves the installation unchanged.


KI-3  "The ASIO Sample Rate has changed" after headphones disconnect
---------------------------------------------------------------------
Status: FIXED in 0.9.5 (verified on real hardware: Bluetooth case test, no
rate dialog).

Symptom
  - Project at 44.1 kHz. Putting the Bluetooth headphones in their case
    (output device disappears) made Cubase show "The ASIO Sample Rate has
    changed: ASIO 96 kHz, Project 44.1 kHz".

Cause
  - On a device-change reset the driver re-read SampleRate from config.ini
    (96000, left by the automatic test) instead of keeping the rate the host
    had set with setSampleRate (44100). Cubase also recreates the driver
    object after the reset, so a per-instance flag was not enough.

Fix (0.9.5)
  - The host rate is kept per process and persisted as LastHostRate in
    config.ini. Precedence: host rate of this process > SampleRate=Auto >
    LastHostRate > panel SampleRate. Choosing a rate in the panel clears the
    remembered values. Test T10 "Rate kept" in the automatic test.

Note
  - LastHostRate is shared by all hosts: after using Resolve at 48 kHz,
    Cubase starts at 48 kHz and then sets its project rate (normal; no
    dialog expected because Cubase sets the rate itself when loading).

Related user error during testing
  - The first report of this bug after "installing 0.9.5" was still 0.9.4:
    the installer could not replace the DLL because of hung Cubase
    processes (see KI-2).


KI-4  Microphone warning shown although Input device is "(None)"
-----------------------------------------------------------------
Status: FIXED in 0.9.6.

Symptom
  - Main tab shows "Windows blocks recording - choose (None - no inputs) or
    allow microphone access" with a "Set to None" button, even when
    Input device is already "(None - no inputs)".

Cause
  - The warning is driven by the Windows microphone privacy setting only; it
    does not check whether any input is selected.

Fix (0.9.6)
  - The warning (and its "Set to None" button) is shown only when an input
    device is selected on the panel (Input device other than "(None - no
    inputs)", or at least one extra input) AND Windows denies microphone
    access (privacy setting, or the last open failed with "access denied").
    It follows the selection at once, before Apply. "Set to None" now also
    clears the extra inputs. The direct-monitoring note and the diagnostics
    verdict follow the same rule.


KI-5  44.1 -> 48 kHz conversion uses Hermite instead of sinc
--------------------------------------------------------------
Status: FIXED in 0.9.6.

Observation
  - Log: "Output: rate conversion 44100 -> 48000 Hz, 2 channels: Hermite
    (sinc would cost 12 M MAC/s, budget 150 M)". The fixed-ratio converter
    follows ResamplerQuality=Hermite from config.ini when converting up.
  - Hermite measures about 89 dB SNR at 1 kHz; sinc about 115 dB.

Fix (0.9.6)
  - The fixed-ratio converter uses sinc whenever the CPU budget allows
    (both directions), independent of ResamplerQuality, which now only
    selects the drift resampler. Hermite is used only when an up-conversion
    is over the budget (150 M MAC/s, shared by all converters of a session:
    the inputs get what the output leaves). New log line, e.g.: "Output:
    rate conversion 44100 -> 48000 Hz, 2 channels: sinc (12 M MAC/s, budget
    150 M)". Cost: about 1.45 ms more output latency at 44.1 kHz (reported
    to the host) and more CPU than Hermite (COMPATIBILITY.txt).

KI-7  Cubase plays silence after switching ASIO drivers
--------------------------------------------------------
Status: CONFIRMED - Cubase behaviour, not a driver bug.

Symptom
  - Cubase shows "WASAPI Driver for ASIO" as the ASIO driver, transport runs,
    but nothing is heard and the driver's channel meters do not move.

What the logs showed
  - The driver was running normally (Shared, IAudioClient3, 0 glitches) and
    had accepted the project rate (setSampleRate 48000 -> 44100). The host
    was sending silence.

Cause
  - After switching the ASIO driver in Studio Setup (e.g. to the Generic Low
    Latency ASIO Driver and back), Cubase left the output bus with no device
    ports assigned ("Not Connected" in Audio Connections).

Fix
  - Studio > Audio Connections (F4) > Outputs > Stereo Out > Device Port:
    assign "Out L" and "Out R" of WASAPI Driver for ASIO.

Prevention
  - Keep DeviceChannelNames unchanged between sessions (port names are how
    Cubase restores connections). Add this to the FAQ.


KI-8  Stricter answers to invalid host calls (0.9.8)
-----------------------------------------------------
Status: BY DESIGN (0.9.8 hardening; watch for reports).

What changed
  - Some calls that the ASIO specification does not allow now get the error
    code asio.h defines instead of being accepted silently: start() or any
    query before init() -> ASE_NotPresent; setSampleRate() / controlPanel()
    from inside a buffer callback -> ASE_InvalidMode. Valid calls are
    unchanged; disposeBuffers() and setClockSource(0) still answer ASE_OK in
    every state, as in 0.9.7.
  - The audio thread ends and asks the host for a reset when the output
    device delivers no event for 10 s AND its playback position does not
    move during that time (0.9.7 waited forever and reported "running"
    without callbacks). A device whose position still moves (for example
    right after a resume from Modern Standby) keeps the stream.
  - WasapiDriverTest.exe of 0.9.7 shows no "Engine:" line in T2 with a 0.9.8
    driver (the private engine-information request changed); use the 0.9.8
    test tool.
If a host shows an error message that it did not show with 0.9.7, record a
trace (TRACING.txt): the AsioCall events show the call and the code returned.


KI-9  Arm64X DLL not yet tested on real Windows on Arm hardware (0.9.9)
-----------------------------------------------------------------------
Status: PARTLY CONFIRMED (2026-10) - the native ARM64 half works on real hardware; the ARM64EC half
(emulated x64 hosts) is still untested. Testers welcome.

First field report (Steinberg forum, October 2026): version 0.9.10 on a Lenovo IdeaPad Slim 5x,
Snapdragon X Plus, built-in Qualcomm Aqstic audio, 44.1 kHz, native ARM64 Cubase, Shared mode,
output only. Reported output latency: buffer 256 = 18.1 ms, 128 = 14.4 ms, 64 = 12.9 ms, 32 = 12.2 ms
(the buffer plus a constant ~11.5 ms from the Windows engine period, as expected in Shared mode).
The tester noted that Exclusive mode only added latency on that machine.

What is known
  - WasapiDriverARM64X.dll (native ARM64 + ARM64EC code in one file) is
    built with MSVC by the CI on a GitHub Windows 11 ARM64 runner and checked
    there with dumpbin: the image is ARM64X, it exports exactly the four COM
    entry points and imports no Visual C++ runtime DLL (static runtime). The
    result is the ::notice annotation of the "arm64x" job of every run.
  - A native ARM64 host (Cubase for Arm) has loaded and played through it (see the first
    field report above). An emulated x64 host (ARM64EC half) has not been reported yet. The x64,
    x86 and plain ARM64 DLLs are unchanged and keep their test status.
  - Linker warning LNK4279 (SetFilePointerEx, icall push thunks) is expected
    and considered benign (CODE-REVIEW.txt "0.9.9 MSVC / Arm64X"); a real
    run confirms it (the update download and the diagnostics' file writes
    use that function).
What to do
  - Testers: TEST-GUIDE.txt block Z (install, registry, automatic test as
    an emulated x64 host, a native ARM64 host, a trace that shows which half
    was loaded). Report the results in a GitHub issue, also when everything
    works.
  - Workaround if the Arm64X DLL fails: the portable bin zip without
    WasapiDriverARM64X.dll (delete or rename it, then run install.bat as
    administrator): it registers the plain ARM64 or x64 DLL after the 0.9.8
    question, one architecture at a time. Run uninstall.bat (or uninstall
    the Setup) first.

KI-10 soxr rate conversion adds about 8-10 ms of latency per direction (0.9.10)
------------------------------------------------------------------------------
Status: BY DESIGN (only when soxr is selected; reported exactly; the default
Auto keeps the low-latency sinc).

What is known
  - Since 0.9.10 the internal rate conversion (DAW rate different from the
    device rate, "Low latency" on) can use the SoX Resampler library (soxr
    HQ). It is used ONLY when Advanced tab > Rate conversion is set to
    "soxr (best quality, +8-10 ms)" (FixedRatioEngine=Soxr); the default
    "Auto (Sinc, low latency)" behaves exactly as 0.9.9 and has none of the
    delay described here. Its quality is higher than the
    built-in sinc (about 130 dB SNR instead of 115, no aliasing at all), but
    it filters in FFT blocks, so it must look further ahead: 429 input frames
    (9.7 ms) at 44.1 -> 48 kHz instead of 64 (1.45 ms), about 8.3 ms more on
    the output and the same again on a converted input (round trip about
    +16 ms). Example: 44.1 kHz project, 48 kHz device, buffer 128, 3 ms
    engine period: output latency 20.1 ms instead of 11.9 ms. The look-ahead
    depends on the rate pair: about 8-10 ms for every pair between 44.1 and
    192 kHz, more at 16-32 kHz (48 -> 16 kHz 15.6 ms, 16 -> 44.1 kHz
    26.8 ms, 44.1 -> 22.05 kHz 19.2 ms; sinc 2.9-4 ms there).
  - The extra delay is part of the latencies the driver reports, so
    recording stays in time (offline model: measured round trip = reported
    within 0.5 frame). Only live monitoring through the DAW feels it.
  - Not affected: the DAW at the device's own rate (no conversion), Exclusive
    mode, extra devices and drift correction (they do not use this
    converter).
What to do
  - For the lowest latency with conversion: keep Rate conversion at "Auto
    (Sinc, low latency)" (the default) or "Sinc (low latency)", or set
    Windows and the DAW to the same rate (no conversion at all).
  - The Arm64X DLL is the only build whose soxr code is compiled by MSVC; it
    is built in CI only (see KI-9 for its test status).

KI-11 Input underruns and discontinuities in Shared mode at a 256 buffer (0.9.10)
--------------------------------------------------------------------------------
Status: FIXED (0.9.12), CONFIRMED on 2026-10-25 by TEST-GUIDE.txt block AB
on the same system: Shared 256 and Shared 512 both 0 underruns / 0 drops /
0 discontinuities after 50-85 s, longest interval between wake-ups
11.5 ms (the audio thread was never late).
Note (0.9.14, block AB of 0.9.13 on the same interface): Shared 512 then
counted 6 underruns / 19 discontinuities again (Shared 256: 0/0/0) with a
maximum read gap of 11.5 ms at a 10 ms period and "max per wake 970" =
the whole capture buffer: the ASIO driver read on time; the discontinuity
flag is set by Windows' own capture engine when IT lost data from the
device driver (Yamaha Steinberg USB Driver), and the lost packet is what
the underrun counts. It is intermittent (the 0.9.12 run was clean) and
comes from the device side; nothing in this driver can recover audio the
engine never delivered. Recording with an interface that has its own
driver: use Exclusive mode (no Windows engine in the path). With the
Microsoft class driver for the same interface the 512 test was 0/0/0
(0.9.11). History: 0.9.11 fixed buffer 256 (0 / 0 / 0 after 70 s where
0.9.10 counted 8 underruns / 27 discontinuities) but buffer 512 on the
same system (Yamaha Steinberg USB Driver, 44.1 kHz, no conversion) then
counted 22 underruns / 46 discontinuities in ~85 s: "max per wake 970" =
the whole capture buffer (974 frames), so the capture buffer filled up
(the audio thread did not read it for >= 22 ms, or the capture engine
glitched), and at 512 no late-packet margin was added (512 >= 441), so one
lost packet was an underrun. 0.9.12: the margin of one capture period is
added at every buffer size in Shared mode (and for the loopback source and
the event-driven Exclusive capture), and the "Capture:" line gains two
timing counters ("max gap: wake X ms, read Y ms": longest interval between
output wake-ups / between drains of the input) that tell a late audio
thread from a capture-engine glitch; the input counters also exclude the
first second of a stream (start-up transient). Found in the first
recording test with an audio interface that has inputs.

Symptom
  - Windows 11 x64, Cubase 15, Steinberg UR22mkII through the Microsoft USB
    audio class driver (endpoint "Line (Steinberg UR22mkII)", fixed at
    24 bit / 48000 Hz), project at 44.1 kHz, Shared mode with "Low latency"
    on, microphone on input 1, recording 30 s while a song played.
  - Buffer 512: "Inputs: underruns 0, drops 0, discontinuities 0", clean
    recording. Buffer 256: "underruns 8, drops 0, discontinuities 27" in
    one run (1 / 1 in a second run), audible dropouts in the recording.
    Output glitches 0 in every run.
What the log showed
  - "Output: low-latency Shared (IAudioClient3) period 480 frames at
    48000 Hz; internal rate conversion 44100->48000 Hz (sinc)" and "Input
    open (Shared): buffer 974, period 441, FIFO target 882, same hardware as
    output=1, drift correction=0": the input runs at the DAW rate (its mix
    rate was 44.1 kHz), one 441-frame packet per 10 ms engine period,
    capture buffer of about two periods.
Cause (confirmed by the arithmetic, fixed in 0.9.11)
  - With a 256 buffer the host runs two callbacks per 10 ms wake-up. The
    audio thread drained the capture client only at the start of a wake-up;
    while the host processed its two callbacks (DSP load peaks up to 45 %),
    the small capture buffer overflowed and Windows dropped packets, which
    it flags as discontinuities. Each lost packet then left the FIFO short
    (underrun).
  - Independently, one late packet (the Windows engine delivers with up to
    one period of jitter) with a FIFO target of two periods left the second
    callback of a wake-up without data.
Fix (0.9.11)
  - The capture clients are drained again after every host callback of a
    wake-up (ARCHITECTURE.txt section 62).
  - When the ASIO buffer is shorter than the capture period, the FIFO
    target includes one more capture period (+10 ms of reported input
    latency at 256 with a 441-frame period; logged). Buffers of one period
    or more were unchanged - and failed at 512 (see Status).
Fix (0.9.12)
  - The margin of one capture period is part of the FIFO target at every
    buffer size (Shared, loopback, event-driven Exclusive). Reported input
    latency in Shared mode: + one capture period (about 10 ms with the
    Windows engine at 44.1 / 48 kHz) at every buffer size (0.9.11 added it
    below one period only); to be confirmed by block AB. A later version
    may make the margin adaptive (measured read gap, ROADMAP.txt).
  - "Copy status": "max gap: wake X ms, read Y ms" and "max FIFO fill N
    (now M)"; counters cleared once, one second after the start.
Workaround on 0.9.10 / 0.9.11: buffer 256 (0.9.11) or any buffer with the
counters watched; report the "Capture:" line with the gap values if block
AB still counts underruns or discontinuities on 0.9.12.


KI-12 Mode = Exclusive silently runs Shared when the device is fixed at another rate (0.9.10)
--------------------------------------------------------------------------------------------
Status: EXPLAINED in the status since 0.9.11; opening Exclusive at the
device's fixed rate (with internal conversion) is planned for 1.0.

Symptom
  - Same interface through the Microsoft USB audio class driver: Windows
    shows its default format "2 channel, 24 bit, 48000 Hz" greyed out (the
    device's own firmware or driver fixes the rate). With a 44.1 kHz project
    and Mode = Exclusive, the panel's Mode combo says Exclusive while "Copy
    status" says "Active mode: Shared low latency (IAudioClient3)", and
    nothing explains the difference.
What the log showed
  - "Output: trying Exclusive", "Exclusive: no format accepted at 44100 Hz",
    "Output: Exclusive not available -> Shared", the same for the input.
    The driver tries Exclusive only at the DAW's rate (every container
    format, every channel count) and falls back to Shared, where Windows
    (or the driver's own converter) handles the rate difference.
0.9.11
  - The status line says why: "Active mode: Shared ... (Exclusive not
    available at 44100 Hz; the device is fixed at 48000 Hz by its own
    driver or the Windows default format)", or "(Exclusive refused,
    hr=0x...)" for any other error; the panel's bottom bar shows "Exclusive
    not available, running Shared" in amber; the log line names the
    device's shared-mode rate.
What to do
  - Set the device to the project's rate in the manufacturer's control
    panel (with the manufacturer's driver installed; the UR22mkII accepted
    Exclusive at 44.1 kHz as soon as the Yamaha Steinberg USB Driver was
    installed and set to 44100 Hz), or in Windows > Sound > the device >
    Properties > Advanced > Default format when it is not greyed out, or
    set the project to the device's rate. Otherwise Shared mode works
    (FAQ 21).


KI-13 Input drops in Exclusive mode at a 256 buffer (0.9.10)
------------------------------------------------------------
Status: FIXED (0.9.14), to be confirmed by TEST-GUIDE.txt block AB on real
hardware. History: NOT fixed by 0.9.11 (the limit change only moved the
drop point); NOT fixed by 0.9.12 on the tested interface (the event-driven
capture made the mechanism visible but did not change it, see "What
0.9.12 showed" below); NOT fixed by 0.9.13 (the gate on the capture
stream's own clock refused nothing, see "What 0.9.13 showed"); 0.9.14
gates on the OUTPUT stream's clock.
What 0.9.13 showed (block AB, Exclusive 256, event-driven period 441,
gate on the capture stream's IAudioClock): drops 384, underruns 0,
discontinuities 0, "Capture: pulls 6527 (empty 0, multi-packet 0), max
packet 441, max per wake 441, max FIFO fill 4724 (now 3059), max gap: wake
11.6 ms, read 12.1 ms, gated 0". 6527 drains in ~38 s = 172 per second,
one 441-frame packet taken at every one of them, and the gate refused
NOTHING: the capture stream's IAudioClock of this driver advances by one
period at every drain, i.e. at the same false rate as its packets (1.73x
real time). A clock that lives in the same broken accounting cannot gate
it. Shared 256 in the same run: 0/0/0 (gated 0, as designed: no gate in
Shared mode).
Fix (0.9.14, ARCHITECTURE.txt section 65): the gate's reference is the
OUTPUT stream's IAudioClock when the Exclusive input runs on the same
device (same container id) as an Exclusive output with a usable clock:
one device, one hardware clock, and the output's position is real time
(the output plays with 0 glitches and its glitch detection already uses
that clock). Base taken right after Start on the audio thread; converted
to device frames like the output's glitch detection. When the input is on
another device, the output is Shared, or there is no clock, the gate runs
on the system timer (QueryPerformanceCounter credit, 0.9.13's fallback).
The capture stream's own clock is not used any more. The log says
"capture gate on the output stream's clock (same device)" at open and
"stop: input capture gate: pulls=N gated=M clock=output|qpc" at stop;
the Stats event carries CaptureGateRef (0 none, 1 output clock, 2 timer).
Expected on this interface at Exclusive 256: pulls about 172 per second,
gated about 72 per second, max per wake 441, drops 0, clock=output.
What 0.9.12 showed (block AB, Exclusive, event-driven capture, Yamaha
Steinberg USB Driver, 44.1 kHz, no conversion, nothing plugged in):
  - buffer 256, capture period 441 (device default): drops 427,
    discontinuities 13, underruns 0 in ~42 s; "Capture: pulls 7255 (empty
    3, multi-packet 13), max packet 441, max per wake 882, max FIFO fill
    4795 (now 3984), max gap: wake 11.5 ms, read 19.8 ms". 7255 drains in
    ~42 s = 172 per second = the rate of the 256-frame OUTPUT wake-ups, and
    every drain found a full 441-frame packet: 1.73 times real time.
  - buffer 512, capture period 882 (2 x default, the 0.9.12 rule): drops 0,
    discontinuities 0, underruns 0 in ~44 s; pulls 2180 = about 50 per
    second = one per 882-frame period, packets of 882; reported input
    latency 63.22 ms (too much, see the 0.9.13 period rule).
  Reading: with this driver neither the capture event nor
  GetNextPacketSize marks a real period; whenever the thread asks, the
  driver hands over "one full period", and the event fires at the output
  period. Only the stream's IAudioClock position advanced at real time.
Fix attempt (0.9.13, "capture gate"): an Exclusive capture is drained
only when a clock says a whole new period exists since the frames already
accepted, and never more than that: exactly one period per period,
whatever the driver offers and however often the thread asks. 0.9.13 used
the capture stream's own IAudioClock (system timer as fallback); on this
interface that clock is wrong (see "What 0.9.13 showed"), hence 0.9.14.
The Capture line ends with ", gated N" = the drains refused by the gate.
The capture period is, since 0.9.13, the smallest multiple of the device
default that is >= HALF the ASIO buffer (441 at 512, reported input
latency about 41 ms).
What 0.9.11 showed (new "Capture:" counters, Exclusive 256, Yamaha
Steinberg USB Driver, 44.1 kHz): the capture client delivers a packet of
512 frames (up to 1024) in EVERY wake of the 256-frame output period
(pulls ~170/s, empty 17 of 8368), i.e. it reports twice the real amount of
audio; the FIFO grows 256 frames per wake and the overfill limit discards
(504 drops in ~50 s, 1 per 16.6 wakes, no underruns, no discontinuities).
At 512 the packets are 512 per 512-frame wake and everything is balanced.
The polled Exclusive capture of this driver reports its packets with a
fixed 512-frame granularity whatever periodicity was requested.
Fix (0.9.12): the Exclusive capture is opened event-driven
(AUDCLNT_STREAMFLAGS_EVENTCALLBACK, an event of its own, periodicity =
the smallest multiple of the device's default period that holds one ASIO
buffer, buffer = one period, one packet per event) and drained by the
audio thread when that event fires, before the output service when both
are pending, and between host callbacks when a packet is already
signalled; GetNextPacketSize is no longer interpreted for an Exclusive
capture (ARCHITECTURE.txt section 64). The log says "Input open
(Exclusive, event-driven): ... period N (device default | K x device
default | aligned by the device)"; the status "[... event-driven, period
N]". Known limit (independent review of 0.9.12): the device
double-buffers one capture period, so a packet is lost (a discontinuity
in the counters) only if one host callback lasts longer than that period;
the period is at least one ASIO block and the thread drains before and
between callbacks, so that needs a callback longer than its own block
time, which is an output dropout as well (DSP load above 100 %). Input
latency in Exclusive mode with buffers larger than the device's default
period grows to that multiple (e.g. 512 at 44.1 kHz with a 441-frame
default: period 882). Workaround on 0.9.10 to 0.9.13: buffer 512 or larger
when recording in Exclusive mode.

Symptom
  - Same system, now with the Yamaha Steinberg USB Driver installed and set
    to 44100 Hz; Mode = Exclusive accepted ("Active mode: Exclusive",
    "Line (Steinberg UR22mkII) [2ch int24, period 256 frames]", reported
    latency 17.41 ms in / 17.41 ms out).
  - Buffer 256: the input drop counter grew steadily, about 10 per second
    (25 a few seconds after opening, 240, then 1234 after a 30 s recording
    plus playback), underruns 0, discontinuities 0, output glitches 0. The
    recording was unusable ("sounds horrible"). Buffer 512 (period 512,
    34.83 ms in / out): 0 drops in 60 s.
What the log showed
  - "Exclusive OK: 2ch int24, buffer 256 frames, period 256 frames
    (5.80 ms), device min period 3.00 ms" for the output and "Exclusive OK:
    2ch int24, buffer 1536 frames, period 256 frames (5.80 ms)", "Input
    open (Exclusive): 2ch int24, buffer 1536, period 256, FIFO target 512,
    same hardware as output=1, drift correction=0" for the input (polled
    capture with a buffer of six periods, no drift correction: same clock).
Cause (fixed in 0.9.11)
  - The overfill limit of the input FIFO without drift correction was
    bufSize*2 + target*3 = 2048 frames, and every call above it discarded
    fill - (bufSize + target) frames: with 768 frames waiting after a
    normal read, one capture call delivering 1536 frames (everything the
    capture buffer held: the audio thread serviced it a period late, or
    the device driver delivers in bursts) took the fill to 2304 and 1536
    real frames (35 ms) were thrown away, every time it happened. No
    underrun followed because 768 frames remained. At 512 the limit (4096)
    was never reached.
Fix (0.9.11)
  - The three overfill limits include the whole capture buffer (in ASIO
    frames), and the FIFO capacity grew to match (ARCHITECTURE.txt section
    61). A backlog of the capture buffer is kept, never dropped. New
    counters in "Copy status" ("Capture: pulls ..., max packet ..., max per
    wake ..., max FIFO fill ...") show how the capture client delivers, so
    a report can tell a burst from a real surplus.
Workaround on 0.9.10: buffer 512 or larger when recording in Exclusive
mode.
